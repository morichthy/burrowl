# 文档维护约定

目标：让 AI 和人都能通过少量文档快速理解项目的结构、流程和注意事项；文档少而准确，不重复。

## 术语必须先定义

- 每个主要术语在 [GLOSSARY](GLOSSARY.md) 中有唯一的权威短定义，写明：它是什么、不是什么、代码标识。其他文档首次使用时，用中文名称并链接到这里。
- `mode`、`strategy`、`status` 等多义字段必须带领域限定，例如"阅读策略""重排模式""复核状态"。
- 同一概念只用一个首选名称，别名登记在术语表里。
- 文档审查检查四点：定义存在、首次出现可理解、跨文档一致、能追溯到契约。缺定义属于文档缺陷。

## 一件事在哪里维护

| 内容 | 唯一位置 | 其他文档的边界 |
|---|---|---|
| 产品用途、概念、安装、常用操作、目录维护 | 根 README | 其他文档只给简短解释和链接 |
| 技术栈、模块依赖、状态归属、影响关系、已知差距 | 根 ARCHITECTURE | 不在别处维护第二份影响图 |
| 功能定义、流程伪代码、选项差异、实现文件索引 | docs/CORE | 不展开字段、参数、常数；AI 按需读代码 |
| 细节入口与分类 | docs/README | 只做索引 |
| 文档职责与维护规则 | 本页 | Skill 只引用规则，不复制 |
| 测试选择与风险检查 | docs/TESTING | 具体断言在测试代码里 |
| 选择理由、删除的功能、历史错误、未决讨论 | docs/DEVELOPMENT_HISTORY | 讨论全局方案前读，开发后补记 |
| 跨多个阶段的开发计划：决定编号、契约变更、任务、验收、进度 | docs/design/（设计稿） | 理由只在 DEVELOPMENT_HISTORY 写一次；设计稿不代表功能已实现，某阶段完成后把稳定说明迁到 CORE / ARCHITECTURE，并更新设计稿的进度记录 |
| 术语 | docs/GLOSSARY | — |
| AI 的工作规则与写作标准 | skills/RULES、skills/RECORDING | 各 Skill 引用，不重复 |
| 工具参数、配置字段 | 自动生成的 docs/reference | 不手写参数表 |
| 记录字段与示例 | `memory.contract` 与示例文件（测试保证可通过校验） | 文档只讲职责与写法 |

## 维护闭环

- **局部开发**：按 burrowl-dev-check 定位受影响的文档和 Skill，开发后核对；无关文档不动。
- **全局整合、架构重构、发布或用户要求全面审查**：开发前后完整阅读六份必读文档和全部 Skill，逐项核对。
- 本次计划或结果摘要记下每份相关文档的处置：**已修改 / 已核对无需修改 / 延期及原因**。不要求每个文件都改，但不能把"文档已写"当成"功能已实现"。
- 改了操作或配置：重新生成 docs/reference 和前端类型。改了记录契约：重新生成草案示例并跑示例测试。
- 结构变化后运行 `burrowl validate`，链接、功能说明、契约一致性和真实测试分别报告。

## Skill 的维护

- Skill 只描述流程、判断规则和调用哪些工具；程序已强制的规则只在"程序已保证"中一句带过。
- 改了工具名、参数或行为：检查所有提到它的 Skill（`burrowl skills check` 能发现不存在的工具，但发现不了参数语义的变化）。
- 全局整合或发布时，逐个阅读全部 Skill，检查四点：触发时机、步骤、工具、判断规则是否与现行代码一致。
- 用户自定义的 Skill 不按名称批量覆盖（`burrowl skills install` 默认不覆盖被修改过的文件）。

## 控制文档增长，保留历史

- 必读文档只保留跨模块理解必需的内容；参数、示例、完整测试矩阵放到细节入口或代码中。新增文档前先看能否并入现有文件；新增后必须在 docs/README 中能找到。
- 精简时逐项核对：
  - 架构原则、概念边界、状态权威、事务与恢复、权限与版本、AI 与程序的分工、已知差距；
  - 仍然有效的约束必须保留；
  - 移动要记录去向；
  - 被替代的要说明依据，不能只删文字。
- 从现行文档删除被替代的方案、失败教训或验证结果前，先把它归入 DEVELOPMENT_HISTORY 对应的决定。
- 设计目标、用户要求、功能存在、验收通过分开写；历史失败、缺失来源和待审状态不因更新介绍而消失。

这是一项人工和 AI 的开发约定，没有后台文档同步服务。

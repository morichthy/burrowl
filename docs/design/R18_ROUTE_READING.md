# R18 归属判定与阅读会话的衔接：复用筛选结果，关联在实际阅读后由 AI 建立

| 项 | 内容 |
|---|---|
| 状态 | 用户确认（2026-10-11），已实施；D-02 的复用条件在实施时修正，见 §2 与 §6 |
| 适用范围 | 阅读筛选（`services/reading/service.py` 的 `screen`/`preview`/`start`）、归属判定（`services/routing.py`，只读调用方）、RULES 第 2 节、burrowl-work、burrowl-read、MCP 服务说明 |
| 关系 | 在 [R13](R13_OWNER_ROUTING.md) 之后：不改 R13 的决定（判定只给筛选包级线索、确认点 = 第一次写入），只处理判定与随后阅读之间的衔接 |

## 1. 背景（2026-10-11 核对代码）

1. **判定与阅读是两层判断**：`memory.owner_route` 只给筛选包、目标与检查点，AI 不读全文就选出暂定对象，再用 `memory.resume` 完整阅读确认（R13 D-03、D-05）。阅读会话里同样先用筛选包 `reading.assess`，判为相关才 `reading.read`。两者共用 `ReadingService.screen`，但问题不同：前者问"是不是同一目标"，后者问"能不能回答问题"。
2. **同一需求会召回两次**：判定后需要复用已有经验时，`reading.start` 用相同的实现再做一遍召回、筛选包和重排（本机约 1 s，见 R13 §8）。只有输入完全相同时这才是重复；`task` 与 `question` 文本不同、或阅读带了字段条件、对象范围、复核过滤时，召回本来就该不同。
3. **阅读会话的归属只能在开始时给**：`reading.start(owner_id)` 之后没有改的入口。阅读若在确认或新建对象之前开始，会话就不属于任何对象。
4. **关联何时建立没有写清**：关联与固定引用都是记录对记录，由 AI 写记录时判断。规则没有说明判定阶段（只看过筛选包或结构）的印象不应直接写成关联。

## 2. 决定

| 编号 | 决定 | 理由 |
|---|---|---|
| D-01 | **判定不进阅读会话**：`owner_route` 与 `memory.resume` 的判断不写入任何阅读会话；进入会话后照常 `reading.assess`（带 digest 和理由） | 判定是全文阅读前的预判断，问题也不同；会话只记录围绕阅读问题的判断 |
| D-02 | **筛选结果复用**：`screen` 的输入（`plan_id`、语料、对象范围、复核过滤、排除项、字段条件、筛选与重排配置、整份配置、重排模型目录）相同，且**就绪对象集合及这些对象的索引水位行、嵌入模型指纹、投影版本**相同时，直接复用最近一次结果；缺口每次现算后替换。复用结果只放在进程内存（10 分钟、8 条），不落盘；没有命中就照常召回，行为与现在相同。回执标明 `reused_from`（来源与时间） | 检索只读就绪对象的索引，这些相同则召回结果相同；消除重复召回又不新增真源；CLI 每次是新进程，自然不复用 |
| D-03 | **顺序固定**：判定 → `memory.resume` 确认或 `memory.owner_create` 新建 → 需要读已有材料时 `reading.start(owner_id=…)`。为同一需求开阅读时，`question` 沿用判定时的 `task` 文本（以及 `variants`、`protected_terms`），沿用已有对象时 D-02 才能命中；新建对象会立即建检索投影（D-05），召回确实不同，重新召回 | 判定不需要全文，阅读放在归属定下之后，会话天然有归属，不用新增改绑接口 |
| D-05 | **新对象立即建检索投影**（实施中补充）：`memory.owner_create` 与 `memory.owner_adopt` 建完对象即同步索引（只有业务卡时投影只含对象元数据），失败不影响对象建立并如实报告。用户在三种方案中选定（2026-10-11）：新建路径重新召回；不采用"先开阅读再新建并归属会话"（D-03 要改、对象操作依赖阅读会话）与"不建索引、不算缺口"（判定找不到新对象，可能重复新建） | 否则新对象在第一次提交前一直是缺口，阅读总是允许全文补偿，判定也找不到它 |
| D-06 | **所属对象尚无记录时不进入本会话召回**（走查后补充）：`reading.start(owner_id)` 的对象还没有任何记录时，该会话所有召回轮次都排除它，回执 `skipped_owner_ids`、时间线记一笔；已有记录的所属对象照常参与 | 只有业务卡、无可读材料，却因标题与问题高度相似排在第一批最前；已有记录时其 L1 细节可能是 resume 没有展开的 |
| D-04 | **关联在实际阅读或工作之后由 AI 写记录时建立**：判定与续接阶段的印象（"这些对象可能相关"）不直接写成记录或关联；建会话时已能确定的（例如用户指定、本次原件已被对方引用并经阅读确认）在写第一条相关记录时引用；不能确定的留在阅读笔记的 `clues` 与工作清单里，等某一轮读完、验证后再写记录并引用交接给出的固定引用，或 `relations_decide` | 只看过筛选包的关系不够可靠；阅读会话本身随对象更新让笔记失效，按轮验证后写入与之一致 |

## 3. 不做的

- 不让 `owner_route` 建立阅读会话或综合多个对象；跨对象综合仍由阅读会话的 `reading.synthesize` 完成。
- 不新增"改绑阅读会话归属"的接口；不把 `attribution.rejected` 转成关联候选。
- 不强制新对象的第一条记录引用候选对象。

## 5. 验收

- 判定后用同一文本 `reading.start`，诊断显示复用，耗时不含召回与重排；第一批筛选包与不复用时一致。
- 输入或数据有任何变化时不复用（T-2 各项）。
- 规则中写明顺序与关联建立时机；`uv run burrowl skills check` 通过；全量 pytest、ruff、lint-imports 通过。

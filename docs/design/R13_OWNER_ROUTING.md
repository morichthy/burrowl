## 1. 背景、目标与非目标

### 背景

burrowl 的核心是信息资产的持续积累：每次工作的成果落到合适的对象（Owner）里，并与已有资产保持一致的关联。对象内的检索精度不是核心——对象内的续接靠结构导航（`memory.resume` 按 目标 → 检查点 → 概览 读取）和完整阅读。

现状（2026-10-10 核对代码）：

1. **归属完全靠 AI 自由判断**：`memory.owners` 只列出全部对象，`query` 只做标题和 ID 的子串匹配；判断规则只在 RULES 第 2 节，理由只写进工作清单，事后无从追溯。
2. **简单任务也被引导去检索**：MCP 服务说明要求"开工前先查有没有可续接的对象"，全局自动模式下小项目和简单问答也会触发清单、续接和检索，拖慢响应并产生没有复用价值的记录。
3. **只读路径成本随记录总数增长**：`IndexService.ready_owners` 每次检索都为每个对象读入并校验全部记录，只为取 HEAD。实测 50 个对象 × 100 条记录时这一步约 3.6 s。
4. **没有全局的关键操作视图**：建了哪些对象、往哪里保存了什么、复核了什么，只能逐个对象翻时间线。

### 目标

1. **该轻则轻**：简单问答零工具调用；一次性小任务不在开工时召回，没有复用价值就不记录。
2. **归属有据、可回退**：需要归属时，用与默认阅读相同的召回给出候选和证据，由 AI 判断；完整阅读后发现不相关，可以换候选或新建，在第一次写入之前没有任何代价。
3. **关键操作可见、可追溯**：工作台和对话里都能看到精简的关键操作记录，每条能追到原始回执或记录。
4. **成本有界**：读取量与候选数成正比，与记录总数无关。

### 非目标

- 程序不替 AI 决定归属，不给"建议动作"，不自动建对象或写入。
- 不另建一套召回：对象级召回与阅读会话共用同一实现。
- 不为操作记录新建持久状态。
- 不提供跨对象的记录迁移事务（单 Owner 事务边界不变）。

## 2. 已定决定

| 编号 | 决定 | 一句话理由 |
|---|---|---|
| D-01 | **投入分三档**，取能完成任务的最低一档：档 0 直接回答；档 1 一次性小任务；档 2 持续工作 | 大量交互是简单问题和小项目，按最重流程处理既慢又产生噪声记录 |
| D-02 | **惰性归属**：只在第一次需要读历史或第一次需要保存时判定；档 0 从不判定，档 1 只在沉淀检查认为值得保存时判定 | 召回成本只由真正要积累资产的任务承担 |
| D-03 | `memory.owner_route` **复用阅读会话的召回与筛选**（`screening.recall` + `screening.packets`：精确身份、关键词、向量三路，RRF 按对象汇总，筛选包窗口按配置重排），但**不建立阅读会话、不读完整材料** | 一套召回一种行为，避免两套实现各自演进；选对象只需要筛选包级别的线索 |
| D-04 | 召回之外**只补两类证据**：候选的当前目标与最新检查点（只读这两条指针记录）；给了文件路径时的来源重叠（读图投影的边）。**程序不给建议动作**，由 AI 判断 | 判断"是不是同一目标"是语义工作；来源重叠不靠猜，是资产关联最直接的依据 |
| D-05 | **归属确认点 = 第一次写入**。确认前选定的对象只是暂定：AI 用 `memory.resume` 完整阅读后发现不相关，就换下一个候选或新建，暂定对象里不留任何痕迹 | 回退在写入之前没有代价；写入之后只能走纠错 |
| D-06 | **归属结论随确认点的那次提交保存**：`memory.commit` 请求增加可选字段 `attribution`（动作、判定者、理由、考虑过并放弃的对象及原因），原样存进提交回执。沿用和新建两种情况写法相同，不改任何记录类型的契约 | 回退和判定理由必须可追溯；回执本来就是该次提交的权威说明，也是操作记录的来源 |
| D-07 | **确认后才发现放错**：不跨对象搬运。在正确对象中重新保存并引用原记录，原记录按 superseded 处理或建关联；规则写进 consolidate | 遵守单 Owner 事务边界和不可变历史 |
| D-08 | **关键操作记录是派生视图**：从对象业务卡（创建）、提交回执（保存、撤回）、复核记录、Run 登记、中枢发布记录实时汇总，不新增持久状态；每条带可追溯的引用 | 事实已在权威数据里，另存一份日志就是第二份真源 |
| D-09 | **只记会改变资产的操作，每条一行**：建立/采用对象、归属确认（含回退）、保存（每次提交一行，按层级计数）、复核状态变化、Run 完成或失败、发布。检索、阅读、归属判定调用、来源登记、索引补齐不记 | 展示要精简，只体现关键操作 |
| D-10 | **两处展示**：工作台首页"最近关键操作"面板（操作 `memory.activity`，CLI `burrowl call memory.activity`）；会改变资产的写操作在返回值里带一行 `activity` 摘要，AI 在回复中原样报告 | 用户要求工作台和对话两处都能看到 |
| D-11 | **准确性优先于速度**：归属判定保持与阅读会话第一轮完全一致的召回、筛选包与重排（为全部召回对象生成筛选包），不为省时降级。秒级到分钟级的耗时可以接受（用户 2026-10-10 确认） | AI 问答本身是秒级，持续工作可接受分钟级检索；归属判错的代价远大于多等一秒 |

## 3. 投入分级（D-01、D-02）

| 档 | 典型任务 | 开工时 | 结束时 |
|---|---|---|---|
| 0 直接回答 | 概念解释、短计算、读源码或配置、查命令状态、闲聊 | 不调用 burrowl 工具 | 不记录 |
| 1 一次性小任务 | 小脚本、改一处配置、一次性数据转换、单轮分析 | 不召回、不判定归属 | 沉淀检查：有内容才 `owner_route` → 确认 → 保存；否则不写 |
| 2 持续工作 | 研究、实验、多步项目、导入资料、续接、用户要求留痕 | `owner_route` → 完整阅读暂定对象 → 确认或回退 | 按 work / consolidate 保存、交接 |

- **升到档 2**（任一成立）：用户说"继续""接着上次""记下来""留痕"或指定了对象；任务多轮多步，或会产生以后要引用的文件、Run、结论；需要复用已有经验或跨材料查找。
- **降档**：用户说"不用记""随便看看"时按档 0/1 处理。
- **沉淀检查**（任一为"是"才保存）：产生了可脱离上下文复用的方法、判断或边界；发现了失败、反例或参数边界；产生了以后要引用的脚本、数据或 Run；用户要求保存。"做完了一件事"不构成保存理由。

## 4. 归属判定与回退（D-03 至 D-07）

### 4.1 流程

```text
memory_owner_route(task, keywords?, paths?, owner_hint?)
    召回：screening.recall(discovery, group=owner) —— 与 reading.start 相同的三路召回与融合
    筛选包：screening.packets —— 与阅读会话相同的窗口选择与重排配置
    补充证据：前 K 个候选的目标与最新检查点；paths 的来源重叠
    → 返回候选（筛选包 + 证据），不给建议动作
AI 判断 → 选出暂定对象（或直接新建；多个都像时问用户）
memory_resume(暂定对象) —— 完整阅读目标、检查点、概览
    ├ 是同一目标或其子任务 → 第一次保存 = 确认归属（该次 memory_commit 带 attribution）
    └ 不相关 → 换下一个候选再读，或 memory_owner_create 新建
               新对象第一次 memory_commit 的 attribution.rejected 记下放弃的对象和原因
```

规则要点（写进 RULES 第 2 节）：

- 确认点之前不向暂定对象写任何记录（包括目标、检查点）。
- 只有主题相似、没有来源重叠和目标一致的证据时，不沿用。
- `owner_hint`（用户指定）优先；目录名不是判断依据。
- `gaps` 里有索引缺口时，不能因为"没有候选"就新建：先 `index.reconcile` 或问用户。

### 4.2 输入

| 参数 | 含义 |
|---|---|
| `task` | 必填。一两句话写清本次任务的目标和交付物 |
| `variants`、`protected_terms` | 可选。等义改写与必须原样保留的词，含义与 `reading.start` 相同 |
| `paths` | 可选。本次任务涉及的文件：绝对路径或 SRC- ID |
| `owner_hint` | 可选。用户指定的对象 ID（Run 映射到其父对象） |
| `limit` | 候选数，默认 5，最大 10 |

### 4.3 输出

```text
{
  task,
  candidates: [{
      owner: {owner_id, owner_type, title, native_path},
      packet: {score, channels, windows[]},          # 与阅读会话的筛选包相同
      goal: {record_id, objective} | null,
      checkpoint: {record_id, title, next_step} | null,
      evidence: [{signal: user_specified | source_overlap | directory_affinity, detail}]
  }],
  gaps: [...],          # 索引缺口、图投影缺口、路径未登记
  diagnostics: {reranking, rerank_items},
  cost: {elapsed_ms, pointer_reads}
}
```

候选按召回融合顺序排列；用户指定的对象和有来源重叠的对象即使不在召回前 K 名也补入候选。

### 4.4 提交请求增量（D-06）

`memory.commit` 请求增加可选字段，存进回执（不进任何记录的内容指纹）：

```text
attribution: {
  action: continue | create,
  decided_by: user | ai,
  reason: 一句话理由,
  rejected: [{owner_id, reason}]      # 考虑过、完整阅读后放弃的对象
}
```

## 5. 关键操作记录（D-08 至 D-10）

### 5.1 来源与条目

| 条目 | 派生自 | 一行示例 | 追溯到 |
|---|---|---|---|
| 建立 / 采用对象 | 业务卡 `created_at`、`created_by`；owner.json | `建立对象 RES-RANDOM-SUM「随机输入求和误差」· AI` | 对象 |
| 归属确认 | 带 `attribution` 的提交回执 | `新建 RES-X（读过 RES-SUM 后判定不相关）` | 提交回执 |
| 保存 | 提交回执 | `RES-SUM 保存 3 条（L3×1、L1×2）` | 提交回执 |
| 复核 | review 记录 | `结论「排序后误差更小」→ accepted · 用户` | 复核记录 |
| Run | Run 业务卡状态 | `RUN-… 完成` / `失败` | Run |
| 发布 | 中枢的发布执行记录 | `发布 12 条到 WeKnora` | 发布计划 |

撤回、替代、争议都属于"复核"条目。同一提交里的复核与保存合并为一行。

### 5.2 操作与展示

- `memory.activity(owner_id?, kinds?, limit=50, before?)`：按时间倒序分页，每条 `{at, kind, actor, owner_id, summary, ref, cursor}`；`summary` 是一行中文；`next_before` 为下一页游标。
- **工作台首页**："最近关键操作"面板，默认 20 条，点击跳到对象、记录或回执。
- **对话**：`memory.commit`、`memory.owner_create`、`memory.owner_adopt`、`memory.consolidate_apply`、`memory.summary_save`、`review.submit`、`review.batch`、`relations.decide`、`maintenance.apply`、`runs.update`/`runs.execute`、`hub.apply` 的返回值在有关键操作时增加 `activity: ["<一行摘要>", …]`（与 `memory.activity` 中的 `summary` 同一套生成函数）。规则要求 AI 在回复末尾原样列出本轮产生的这些行，不展开。

### 5.3 成本

实时汇总需要遍历各对象的提交链。先实现"按对象倒序读提交清单 + 归并 + 分页"，实测 50 对象 × 100 记录、500 对象的耗时；明显变慢时再加可删除重建的派生缓存（届时补充到 ARCHITECTURE 状态表），不预先引入。

# 开发决策与演进记录

本页回答三个问题：为什么这样开发、从哪些错误中改过来、哪些讨论还没有定案。

- **全局架构或工作流方案讨论前完整阅读**；局部方案按相关决定查阅；开发后补记实际结果。
- 当前功能和模块以 [CORE](CORE.md)、[ARCHITECTURE](../ARCHITECTURE.md) 为准，本页只保存理由，不复制接口手册。
- 每条写清三点：决定、原因、影响或代价。被替代的决定不删除，标明被什么替代。

## 一、从源项目继承、仍然约束开发的选择

源项目 `A_work_auto_flow` 的这些决定在重构中保留，编号沿用源项目，便于追溯。

| 编号 | 决定 | 原因 | 在本项目中的体现 |

| D01 | 复用业务对象（Owner）的身份，用不可变修订和固定引用；保存、索引、复核分开表达 | 另建平行对象会让来源和修订对不上；保存成功不代表索引或结论有效 | `memory_store`、FixedRef、回执中 save_status 与 index_status 分开 |

| D36 | 阅读分 standard / associative / quick 三种策略；联想方向由主 Agent 制定 | 不同问题需要不同的阅读深度；阅读者不应自己决定联想方向 | `strategy`、`reading.recall(mode=association)` |

## 二、本次重构的决定（2026-10-08）

### R1 只支持 memory-v4 现行版本，不迁移旧数据

- **决定**：数据格式直接采用 memory-v4 契约中各类型的现行版本。不写迁移工具，不兼容 v1–v3、event/map 类型和 legacy 阅读会话。
- **原因**：用户确认旧的真实记录不保留；兼容层是源项目复杂度的主要来源。
- **影响**：旧数据目录不能直接打开。测试夹具使用浮点求和样例（本身就是 v4 格式）。

### R2 检索合并为一套：FTS5 + sqlite-vec；Qdrant 只作可选的服务器后端

- **决定**：源项目三份独立的检索代码（原件、记录全文、Owner 发现）合并为一个 `index` 模块，关键词和向量放在同一个 SQLite 文件里。
- **原因**：
  - 三份代码各自建表、同步水位、融合结果，重复且互相反向依赖。
  - Qdrant 本地模式会加排他进程锁，MCP 和工作台两个进程无法同时打开；它的检索实际上是 numpy 暴力计算。
- **影响**：`index.vector.kind` 预留了 `qdrant-server`，但适配器**尚未实现**（约 10 万向量以上再做）。

### R3 一个操作注册表生成 HTTP / MCP / CLI

- **决定**：所有能力定义为带类型的函数，注册后自动生成三种入口和前端类型。
- **原因**：避免三套接口参数不一致。
- **影响**：
  - effect=`user` 的操作（复核确认、批准全文补偿、执行发布、停用来源、保存视图）不暴露给 agent。
  - MCP 写操作失败时以 ToolError 返回 Problem JSON。

### R4 外部知识系统做成可插拔连接器，本地是唯一权威

- **决定**：WeKnora、Markdown 库等作为发布目标与检索来源。默认只发布已复核的 L4/L3 与依据完整的成稿文档；撤回或复核失效时删除或标记外部条目。
- **原因**：WeKnora 擅长收集整合、检索和 Wiki，且由专业团队维护；但版本变化快，不能作为权威数据。
- **影响**：
  - WeKnora 的接口细节集中在 `api_v08.py`，新版本另加一层。
  - 宿主 AI 编写的 Wiki 先作为本地 `wiki_page` 记录提交。
  - WeKnora 已部署在本机（v0.8.2），但连接器尚未连真实服务实测。

### R5 阅读交互：工作台实时页 + MCP 询问

- **决定**：
  - agent 通过 `reading.*` 推进会话；用户在工作台实时查看并操作，操作进入收件箱，随下一次响应交付。
  - 需要批准的动作走 `reading.ask_user`：支持 elicitation 的宿主在对话中弹窗，否则回退到工作台。
- **影响**：标准阅读从 14–18 次调用降到约 6–9 次，调用前不再需要先写 JSON 文件。

### R6 Skill 合并为 4 个，规则只写一次（2026-10-08 修订）

- **决定**：
  - 源项目 8 个 Skill 合并为 burrowl-work / burrowl-read / burrowl-consolidate / burrowl-dev-check。
  - 公共规则写在 skills/RULES.md，记录标准写在 skills/RECORDING.md。
  - 程序已强制的规则在 Skill 中只一句带过。
- **原因**：源项目开工前要加载 5–7 万 token，同一条规则重复写 3–7 次。
- **修订**：初版过度精简，丢失了必要的定义和判断规则（见第四部分 E1），已补回。现在 4 个 Skill 加 RULES、RECORDING 共约 580 行，仍远少于源项目。

### R7 工作台前端：薄客户端，只调用操作接口

- **决定**：前端按功能分目录；所有数据通过 `POST api/v1/ops/<name>` 获取；参数类型由操作注册表生成；阅读会话页用 SSE 刷新。
- **原因**：源项目前端约 2.2 万行，其中大量是各接口的手写类型和重复的状态管理。
- **影响**：
  - 没有引入 TanStack Query，用约 100 行的 `useOp` / `useAction` 代替。
  - 依赖版本与源项目一致，可以离线安装。
  - 浏览器端到端测试使用系统自带的 Edge。

### R8 离线安装包与模型

- **决定**：
  - 安装包内置独立 CPython（取自 uv 管理的 python-build-standalone 解释器），依赖在构建时装好。
  - 每个版本独立目录，用目录联接 `current` 切换或回滚。
  - 模型放在本机共享目录，用 `burrowl models install` 安装。
  - MCP 宿主配置直接调用 `current\python\python.exe`。
- **原因**：
  - 宿主通过 cmd.exe 启动带空格路径的 `.cmd` 会出错。
  - cmd 按控制台代码页（GBK）读取 `.cmd` 文件，`.cmd` 里只能用纯 ASCII。
- **影响**：数据目录和安装目录都可以含中文与空格，已实测。

- **修订（2026-10-09，安装更新局部补修）**：工作台修改后仍安装了此前生成的同版本 zip，使旧内容再次覆盖安装目录。同版本同步逻辑保留；另修复重复构建时运行时内容相同、时间不同仍被复制，导致已运行 Python/DLL 占用阻挡安装的问题：先核对 SHA256，仅对相同内容跳过覆盖，通常对齐时间，严格占用时精确排除该文件，真实内容变化仍正常复制或提示关闭占用服务。新增 `packaging/build.py --install [--root ...]`，先完整构建，再从生成目录直接安装，不生成 zip。构建增加 `BUILD_INFO.json`，安装输出显示来源、根目录、提交和时间，并明确提示重启工作台/MCP及刷新浏览器。源码、生成目录、发布包、安装文件与已运行进程分别核对，不能只凭版本号宣称更新已生效。

### R9 可移植包（burrowl-bundle）同时承担备份、恢复和迁移

- **决定**：整个数据目录按字节打包，附逐文件 sha256 清单；排除可重建的索引和中枢映射；恢复先完整校验，只写入空目录。
- **原因**：源项目的 portable 快照和迁移工具都依赖旧格式；新格式下按字节原样搬运即可保持所有固定引用有效。
- **影响**：外部原件（数据目录外的已登记文件）不打包，只在清单中列出；恢复后用 `sources.relocate` 指向新位置。
- **修订（2026-10-08）**：用户要求迁移时外部原件一同打包并自动重定向。改为：
  - 来源登记增加**工作根**，工作目录里的来源记为"根 + 相对路径"，整个目录搬家只改根；
  - 默认打包与登记指纹一致的外部原件（变化或缺失的只列入清单，因为固定引用指向登记时的内容）；
  - 恢复时先规划全部去向（映射 → 原位置不动 → 并列的 `<目录名>-work/`），有冲突就整体中止，再写入并改写来源登记。
  - 工作目录中未登记的文件（仓库其余部分、虚拟环境）不打包：只有被引用的原件才影响记忆的完整性。

### R11 项目改名为 burrowl（2026-10-08）

- **决定**：项目由 rdwork 改名为 burrowl（burrow 深洞贮藏 + owl 研究与智慧），全部统一：Python 包 `burrowl`、命令 `burrowl`、MCP 服务名、环境变量 `BURROWL_*`、数据目录状态 `.burrowl/`、项目标记 `.burrowl.json`、迁移包格式 `burrowl-bundle/1`、凭据前缀 `keyring:burrowl/`、安装目录 `%LOCALAPPDATA%\burrowl`。Skill 改为 burrowl-work / burrowl-read / burrowl-consolidate / burrowl-dev-check。
- **原因**：Skill 会装到客户端的全局目录，work、read 这类不带限定词的名字会和其他 Skill 冲突，也看不出归属。尚未正式发布，是改名成本最低的时候。
- **影响**：旧名称不保留兼容；之前用 rdwork 安装或接入的环境需要用新安装包重装并重新运行 `burrowl connect`。

### R10 接入方式是宿主配置，不是数据目录配置

- **决定**：数据目录、工作目录和运行模式（auto / manual）写在宿主 MCP 配置的启动参数里；`mcp.mode` 只作为未给参数时的默认值。auto 模式通过 MCP 服务说明（instructions）让宿主在每次对话中默认采用 burrowl-work / burrowl-read / burrowl-consolidate。
- **原因**：同一数据目录可以被多个项目、多个宿主使用，每个项目的工作目录不同；用户希望接入后"默认就按这套方式工作"，又能按项目关闭。
- **影响**：`burrowl connect` 一步完成数据目录、`.mcp.json` 与 Skill；burrowl-dev-check 默认不安装。
- **修订（2026-10-08）**：用户要求接入面向通用 agent，而不是优先 Claude；manual 要能按项目开启。改为：
  - `burrowl connect -c <客户端>` 按客户端写配置（generic、claude-code、codex、cursor、vscode、gemini、claude-desktop），默认用户级；
  - Skill 只装进原生支持 SKILL.md 的客户端；其余客户端由 MCP 工具 `system.guide` 提供同样的全文。MCP prompts 通常只能由用户触发，agent 读不到，所以不能作为唯一通道；
  - **再修订（同日）**：用户要求不要替各 agent 决定 MCP 和 Skill 的安装细节。删除按客户端写配置的 `connect`，改为 `burrowl mcp-config` 输出标准 MCP 配置、`burrowl skills install <目录>` / `skills pack`，由客户端里的 agent 按自己客户端的规范登记（各客户端的配置位置变化快，写死在程序里易过时，例如 Codex 的用户级 Skill 目录已从 `~/.codex/skills` 改为 `~/.agents/skills`）。Skill 安装目录与文件指纹记入安装根目录下的 `burrowl-install.json`，setup 切换版本后自动执行 `burrowl upgrade`，只替换和删除用户没改过的文件；setup 记住安装根目录（用户环境变量 `BURROWL_ROOT`）。
  - 安装根目录不放在 AppData：从 MSIX 打包的客户端（Claude 桌面版）中运行时 AppData 写入会被重定向到该应用私有目录，`current` 联接失效、其他程序也看不到；setup 检测到时报错。
  - 项目开关 `burrowl enable / disable`：写 `.burrowl.json`（MCP 服务启动时按工作目录读取，manual 下启用、auto 下关闭），并在 AGENTS.md（及已存在的 CLAUDE.md / GEMINI.md）中维护标记块，让不读 MCP 服务说明的客户端也知道。

### R12 知识图谱与检索升级（2026-10-09）

- **决定**：本地检索从"传统 RAG"升级为"自然单元嵌入 + 人和 AI 共同整理的知识图"，同时定义对外交换格式。完整的设计、契约变更和分阶段任务见 [设计稿 R12](design/R12_KNOWLEDGE_GRAPH_RETRIEVAL.md)（决定编号 D-01 至 D-28）。要点：
  - 规范记录是唯一真源；本地索引（含新增的图投影）、交换包（Markdown 库 + 图 JSONL）、外部系统的索引都是派生数据。
  - 核心资产 = 记录契约 + 整理图（概念、关联、合并判断、结论之间的关系）+ 复核与成熟度 + 来源追踪。自动构图、高级图算法、自动 Wiki、浏览界面可以交给外部工具。
  - 层级职责不变；新增与层级正交的知识节点（结论、概念）；L1 可以写结论；正文使用可读链接，提交时由程序固定版本。
  - 所有关系用一套边属性画在同一张图上；结论是节点，带条件的关系挂在结论上。
  - 成熟度分四级，存在复核记录里；最高级"已确立"只能由人或经授权的验证流程确认，程序强制执行。
  - 本地保留关键词、向量和内置图路线三路基线检索；外部检索是可选的一路，命中必须回到本地核验。
  - 先修复向量截断（E6）、建立评估集，再逐步上线，每一步都用同一评估集比较。
- **背景**：用户提出传统 RAG 的两个不足：
  1. 分块不准导致召回不准。用户设想加大上下文、按自然段落嵌入，并带上必要的上下文。
  2. 知识之间缺少关联。用户设想 Wiki 式的文档互引图谱（参考 WeKnora 和 Obsidian），以及一张随新知识增量维护的知识网络，并问网络存多大的颗粒合适。
- **演进过程**（六轮讨论，每轮修正了上一轮的一部分）：
  1. **调研与实测**：
     - 读现有代码时发现，嵌入模型实际只读取每个窗口的前 128 token（E6）。所以分块问题的主因是"窗口太小"，不是"边界切错"。
     - 浮点样例中每条记录都在 2k token 以内，因此换长上下文模型后可以整条嵌入。
     - 提出"上下文信封 + 整体嵌入"：按结构补上下文，不调 LLM，作者写好的检索说明就是上下文。关联方面提出"概念层 + 结论节点，合成一张图"，并要求评估集先行。
  2. **对照另一个 agent 的方案**，形成以下共识：
     - 保存单位、检索单位、阅读单位要分开考虑；
     - 一份完整内容可以有多个检索入口；
     - 先做"保存时补上下文"，late chunking 作为独立对照；
     - 以"有条件的主张"作为知识节点；
     - Wiki 与知识网络共用身份和来源。

     同时修正了它的一个判断：它认为问题在于"360 token 切窗打断了自然边界"，实际问题是窗口只读入了 128 token。
  3. **用户提出维护精力有限**，问应该自己持续维护，还是把 L0–L4 定义好、接入别人维护的系统。当时的提议是：核心收缩到记录契约、复核与来源追踪，图和 Wiki 整体交给外部。**此提议在下一轮被修正**。
  4. **用户指出**：人工加入概念、建立连接、持续维护节点之间的关系，本身也是核心；复核还可以细分出确信程度、使用情况、初步反例。由此修正为两点：
     - 区分"整理图"和"自动图"：整理图是权威数据，留在本地；自动图是候选，可以外包。
     - 复核拆成四个维度：复核状态、证据成熟度、支持与反例、实际使用。

     同时调研了不需要 Docker 的本地工具（LightRAG、Cognee、GraphRAG、qmd、Obsidian）。
  5. **用户要求**：本地必须有内置图检索作为回退；问外部工具是否只能读原文；问内部图和外部图怎样保持一致。由此确定：
     - 内置图检索在 SQLite 中自研，不用 LightRAG 做回退；
     - 外部工具有三种输入方式：原文自抽、直接导入图、读 Markdown 链接；
     - 一个真源，三种派生；
     - 外部与内部只在边界上保持一致；
     - 在内部模型和各工具适配器之间加一层我们自己定义、带版本的交换格式；
     - "AI 只写需要判断的内容，能推出来的一律由程序推"的字段原则。
  6. **用户追问**：L0–L4 要不要改；关联、概念合并、结论具体怎么实现；最高等级是否只限工程验证；文稿、Markdown 库、关联和复核能否统一；多种关系是否分开画；结论定义的关系怎样体现；链接的可读性。由此确定：
     - 层级不重写，只补四条定义；
     - 关联增加确定度、提出者、发现场合，新增 `related_to`，快速添加默认为"related_to + 猜测"；
     - 概念的合并和拆分用修订表达；
     - "已确立"按四类证据认定，与 accepted 是同一道门；
     - 一种链接写法 + 一个渲染器生成所有视图；
     - 统一边模型和通用抽边；结论节点 + 快捷边；
     - 全库一个概念库，可以按领域筛选；
     - 可读的 handle 链接。
- **被放弃或暂缓的方法及其问题**：

| 方法 | 问题 | 现在的处理 |
|---|---|---|
| 精细调整切分规则，或让 LLM 决定切分点 | 用户没有时间维护；2026 年的复现研究显示，在全库检索中简单按结构切分优于 LLM 引导的切分；L1–L4 和技术块本身就是结构 | 按现有结构切分；只有 L0 原件需要切分 |
| 只换大上下文模型，不补上下文 | 长文本被压成一个向量时，局部事实会被主题淹没；块中缺少定义和条件 | 上下文信封 + 记录级和块级两种向量 |
| 嵌入前为每块调 LLM 生成上下文（Anthropic Contextual Retrieval 的做法） | burrowl 没有内置 LLM；建索引成本高；作者写好的检索说明、概览已经提供了同样的信息 | 用确定性的信封拼装已有字段 |
| 与信封同时上线 late chunking | 无法判断收益来自哪里；需要双向编码器；文献显示它对全库检索有利，但对单篇内定位不利 | 作为 P1 之后的独立对照实验 |
| 把同一段概览复制到每个块 | 不同块的向量趋于相似，降低区分度 | 信封只放标题链和简短字段 |
| 以"实体—关系—实体"三元组为知识网络的颗粒（GraphRAG、LightRAG、Mem0 的默认做法） | 上下文塌缩：丢失条件、版本、比较基准和反例；而研发结论几乎都是有条件的 | 结论是节点，带条件的关系挂在结论上，另派生快捷边 |
| 像 A-MEM 那样，新知识进来时改写旧笔记 | 不留历史，违背不可变修订 | 只出新修订；候选由 AI 判断 |
| Graphiti 式的双时间事实边 | 需要图数据库；提交历史、适用范围和复核状态已经表达了"何时得知"和"何时成立"；"条件不同"不等于"旧事实过期" | 不采用；借鉴"标记失效而不删除" |
| Wiki 图谱和知识网络做成两套系统 | 两份真源，会逐渐不一致 | 一张图：概念页是节点，Wiki 是它的阅读视图 |
| 图和 Wiki 整体交给外部（第 3 轮的提议） | 整理图是核心资产；外部不可用时会失去联想能力 | 整理图留在本地；外部只承担自动构图和额外召回 |
| 用 LightRAG 做本地回退 | 查询时仍要调 LLM；自带存储，多一份副本；依赖重、接口变动频繁 | 在 SQLite 中自研图路线；LightRAG 改为外部连接器 |
| 以 Markdown 为真源，或在本地另存一份图数据作为真源 | 不可变历史、指纹、写入校验难以保证；多份真源要同步 | 都是从记录派生的视图 |
| 要求外部系统的图与内部一致 | 外部的构图方式不受控制 | 只保证版本对账、回源核验、整理边单向导出 |
| 每接一个工具，就直接从内部模型写一个适配器 | 内部字段一变，所有适配器都要改 | 中间加一层带版本的交换格式 |
| 把成熟度写进记录内容（例如复用 `knowledge_facets.confidence`） | 复核绑定内容指纹，每次评估都会让复核失效，形成死循环 | 成熟度存在复核记录里 |
| 用主观概率表示确信程度 | 难以校准，不同人和 AI 之间不可比 | 用有判定标准的四级证据阶梯 |
| 把复核信息压缩成一个等级 | 各维度性质不同，谁有权给出也不同 | 拆成四个维度，其中两个是派生统计 |
| 最高等级只认工程验证 | 严格证明、公认结果同样可以充分可靠 | 按四类证据认定，门槛不降低 |
| 把关系类型和确定度合并成一个字段 | 无法区分"确定有关但说不清类型"和"怀疑是同一失败模式" | 存两个字段，快速添加时只需要填一句说明 |
| 链接里直接写 `MEM-<UUID>` | 人读不懂 | 使用可读的 handle 和结论短名，由程序固定版本 |
| 按领域分成多个概念库 | 会切断跨领域的类比和迁移 | 一个概念库，按领域筛选 |
| 把 WeKnora 作为必需组件 | 需要 Docker；对个人本地使用太重 | 保留为可选的中心库 |
| 每次提交时调 LLM 抽取实体 | 成本高；burrowl 没有内置 LLM；与"语义判断由 AI 负责"冲突 | 语义工作在收口时由宿主 AI 完成 |
| 社区摘要（GraphRAG global search）、RAPTOR 递归摘要树 | 现有 L2–L4 已经是多粒度摘要；没有证据表明需要 | 不做 |

- **影响与代价**：
  - 契约只做增量（新字段可选，不提升版本），已有复核不受影响。
  - 新增的派生状态：图投影、`link_candidates`、`exports/`、`eval/`。
  - 新增的规则：链接写法、L1 写结论、概念页、成熟度权限。
  - 嵌入模型可能变为 0.6B 级别，CPU 上重建索引变慢，需要实测。
  - 图路线默认关闭，等评估后再决定是否打开。
- **外部依据**（调研于 2026-10-08 至 10-09；数字多为论文或厂商自报，仅作方向参考）：
  - 切分与上下文：[Beyond Chunk-Then-Embed（2026）](https://arxiv.org/abs/2602.16974)，按结构切分在全库检索中优于 LLM 切分；[标题链前缀（2026）](https://arxiv.org/abs/2608.00824)，MRR@5 从 0.374 升到 0.463，并指出了"测量陷阱"；[Late Chunking](https://arxiv.org/abs/2409.04701)；Anthropic Contextual Retrieval（失败率降低 35%、49%、67%）。
  - 图与颗粒度：[RAG vs GraphRAG](https://arxiv.org/html/2502.11371v3) 与 [When to use Graphs in RAG](https://arxiv.org/pdf/2506.05690)，图对多跳问题有益，对简单查找可能有害；HippoRAG 2、AtomicRAG、GRASP（命题颗粒）；A-MEM、Mem0、Graphiti（记忆系统的颗粒度和时间模型）。
  - Wiki：本地 WeKnora v0.8.2 文档（`website-docs/03-features/14-wiki.md`：候选抽取 → 逐块引文 → 去重"相关不等于相同" → 合并 → 不用 LLM 的收尾）；[Karpathy 的 LLM Wiki 模式](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)；[llm-atomic-wiki](https://github.com/cablate/llm-atomic-wiki)（原子层和两层体检）。
  - 工具：[LightRAG](https://github.com/HKUDS/LightRAG)（文件存储、自定义图导入）；GraphRAG 的"自带图"；Cognee（默认图库 Kuzu 已于 2025 年 10 月停止维护，迁移到 Ladybug）；qmd（本地 Markdown 混合检索）。
  - 另一个 agent 的调研备忘保存在用户数据目录的研究对象 `RES-BURROWL-RETRIEVAL-EVOLUTION` 中，不在仓库里。
- **实施记录（2026-10-09）**：P0–P3 完成，P4 完成中枢路线与外部候选回流；逐项进度、评估数字和偏离见设计稿 §10。实施中得到的结论：
  - **长上下文模型没有带来融合后的收益**。Qwen3-Embedding-0.6B-Q 单看向量通道略好，但融合后 MRR 低于 MiniLM（0.785 对 0.885，13 题），查询慢约 17 倍、重建慢约 20 倍、内存约 7 倍。修好截断并加上下文信封后，MiniLM 已经覆盖了大部分收益。默认模型暂不更换，等真实数据题集再测。
  - **图路线在单对象样例上测不出增量**（B4 与 B3 相同）。图的价值依赖概念链接和关联，需要真实数据积累后再评估，保持默认关闭。
  - **LightRAG 的自定义图导入不能按文档删除**（T-P4.0 实测 1.5.7：`insert_custom_kg` 不写文档状态，`adelete_by_doc_id` 返回 not_found，实体保留）。与 D-22"可以按文档删除"的假设不符。用户选定"按需重建 + 嵌入缓存 + 后台替换"：只有新增时追加，有修改或删除时在新目录整体重建、成功后切换；未变内容的嵌入来自缓存。这与本地索引的做法同理——本地也是按对象整体重算投影，只是每一行都记着声明者，可以精确删除；LightRAG 按名字合并实体、不记来源，所以只能把重建范围放到整个工作目录。被放弃的替代方案：逐个删除实体和关系（共享概念要做引用计数，易错）；只用文本模式（要配 LLM，放弃整理图）。查询侧符合预期：给定关键词时只取上下文不调用 LLM。另外两个实测细节：LightRAG 默认的 tiktoken 首次使用要联网，改用逐字符分词；它会规范化 chunk 的 file_path，所以写入由 local_key 派生的标记。
  - `requested_maturity` 放宽为可与 accepted 一起提交，原因是按原文提议升级要先把已确认的复核降级（待用户确认）。

### R13 归属判定、投入分级与关键操作记录（2026-10-10）

- **决定**：完整设计见 [设计稿 R13](design/R13_OWNER_ROUTING.md)（D-01 至 D-11）。要点：
  - 投入分三档：简单问答不调用 burrowl；一次性小任务开工不检索、结束时沉淀检查有内容才记录；持续工作才在开工时判定归属。
  - 归属判定 `memory.owner_route` 复用阅读会话第一轮的召回与筛选包，只补目标、检查点与来源重叠证据，不给建议动作，由 AI 判断。
  - 第一次写入才算确认归属，确认前可换候选或新建；归属说明 `attribution` 随该次提交存进回执。
  - 关键操作记录是从权威数据实时汇总的派生视图，在工作台首页和写操作返回值两处展示，每条一行。
- **背景**：用户指出 burrowl 的核心是信息资产按合适的关联持续积累，不是对象内的检索精度；之前的多数据集评测测的是"单个对象内大语料的记录级 R@k"，与目标不对齐。同时担心简单项目被大量召回拖慢、产生没必要的记录；要求关键操作能在控制台精简展示和追溯。
- **演进过程**（同日三轮）：
  1. 第一版做了带 fast/full 模式和决策表（continue / create / ask_user）的路由操作，fast 模式关掉向量路以求快。用户指出：开发前没有先确认方案；对象级召回应与默认召回策略一致，由 AI 判断。
  2. 实测发现之前检索慢的主因不是向量路，而是 `ready_owners` 每次检索都为每个对象读入全部记录只为取 HEAD（50 对象 × 100 记录约 3.6 s → 改为 `read_head` 后约 0.25 s）。"关闭向量路"没有依据，改为复用阅读会话的召回实现；决策表的"建议动作"本质是语义判断，删掉。
  3. 用户补充：完整阅读后发现不相关应能回退；关键操作要在工作台和对话两处精简展示。由此确定"确认点 = 第一次写入"和派生的关键操作记录。
- **被放弃的方法**：

| 方法 | 问题 | 现在的处理 |
|---|---|---|
| 归属路由单独一套召回（只走关键词） | 两套召回各自演进，行为不一致；速度理由没有实测依据 | 复用 `ReadingService.screen` |
| 程序按决策表给建议动作 | "是不是同一目标"是语义判断；建议容易被当成结论 | 只给证据，AI 判断 |
| 归属说明写进 goal 记录 | 沿用已有对象且目标不变时没有地方写 | 存进确认点那次提交的回执 |
| 单独保存操作日志 | 第二份真源，丢失或与回执不一致时无法判断谁对 | 从权威数据实时汇总 |
| 跨对象搬运放错的记录 | 违背单 Owner 事务边界和不可变历史 | 在正确对象重新保存并引用原记录 |

- **耗时取舍**：实测归属判定约 1.3 s（主要在为全部召回对象生成并重排筛选包）。用户确认准确性优先，持续工作可接受分钟级检索，不为省时与阅读召回分叉（D-11）。
- **影响与代价**：提交请求与回执增加可选的 `attribution`（schema 增量）；`runs.update` 把状态改为结束时补记 `ended_at`；确认前不写入暂定对象，第一条中间成果会晚一些落盘；关键操作记录的读取随对象数增长，对象很多时需要派生缓存。
- **实施记录**：见设计稿 §8。

### R14 Run 作为执行证据（2026-10-10）

- **决定**：完整设计见 [设计稿 R14](design/R14_RUN_EVIDENCE.md)（D-01 至 D-13）。要点：
  - Run 是执行证据，与 L0 同一性质：不持有记忆记录，不进任何检索投影，也不作为归属候选；它的价值通过引用它的正式记录体现，也通过这些记录被找到。
  - 对象扫描不进入 `runs/` 目录；按编号定位 Run（目录名即小写编号），不新增持久状态；上级对象按目录位置判断。
  - 对象内 Run 的知识写进上级对象；独立 Run 的知识按主题写进合适的知识对象，没有非常合适的就放进 knowledge 类型的通用知识对象（概念库仍是配置指定的那一个）。
  - 没有知识的 Run 不保留：当前无引用时可以丢弃，移入回收站。收口时程序报告未被固定的 Run 与 L0。
  - Run 业务卡的 `conclusion` 只写执行摘要，不能作为问题的解决依据。
- **背景**：性能复核发现，保存的剩余耗时主要在对象扫描，而 Run 是增长最快的对象（1200 个 Run 时单次扫描约 1.5 s，按每年 2000 个 Run 估算，第 3 年保存一次约 40 s）。用户随即指出 Run 进扫描不合理，并要求核对 L0 和 Run 是否进入默认检索、有用信息是否都被正式记录固定。核对结果：L0 不进默认检索；Run 会作为对象进入默认发现召回；程序不检查执行证据是否被引用；Run 卡里的自由文本结论可以作为问题的解决依据。
- **被放弃的方法**：

| 方法 | 问题 | 现在的处理 |
|---|---|---|
| 只把发布前复核改成按需扫描或只重读被引用对象（R13 后续的"第 3 步"） | 保存从 5 次扫描降到 1 次，但扫描本身仍随 Run 数增长，Run 多了照样慢 | 让 Run 不参与扫描 |
| 另建 Run 索引文件 | 多一份需要与目录保持一致的状态 | 目录名即编号，按位置直接定位 |
| 把独立 Run 搬到知识对象目录下 | 改变路径；若同时改业务卡还会改变指纹，已有引用失效 | 不搬，被引用即固定 |
| 未被引用的 Run 只报告、由用户清理 | 用户指出没有知识的 Run 本身就不该保存 | AI 丢弃到回收站，清空回收站由用户执行 |
| 为兜底知识新增对象类型 | 现有 knowledge 类型已能承接，代码不限制其数量 | knowledge 分为概念库与通用知识对象 |
| 上级对象按业务卡的 `owner_id` 判断 | 要读全部 Run 卡；与按位置判断的权限检查不一致；样例中有放在研究目录下、`owner_id` 却为空的 Run | 按目录位置判断，不一致时 validate 提示 |

- **影响与代价**：引用格式与指纹不变，已有记录全部有效。Run 不再出现在默认阅读、查询与归属候选中，显式查找用 `runs.search`。关系图删除"上级 → Run"的 produces 边；结论派生统计删除 `run_inputs`（原统计 Run 对象中以 input 引用结论的记录，Run 不再保存记录后恒为 0）。向 RUN- 提交记录、在查询范围中指定 RUN- 会被拒绝。全局关键操作记录与 `runs.search` 改为按目录元数据惰性读 Run 卡。
- **实施记录**：见设计稿 §11。

### R15 工作台笔记交给 AI（2026-10-10）

- **决定**：完整设计见 [设计稿 R15](design/R15_WORKBENCH_NOTES.md)（D-01 至 D-12）。要点：
  - 笔记从"本机偏好"变成用户交给 AI 的待办，但仍不是研究记录。AI 只能读和回写（方案、提问、不处理），新建、交给 AI、执行、退回、清除都由用户在工作台完成。
  - AI 对记忆的写入先给预览：方案是逐步 dry_run 过的 `memory.commit` / `relations.decide` 参数，由用户点"执行"后服务端原样写入；执行前核对各目标对象的 HEAD，变化就不写、退回 AI。
  - 处理完默认折叠保留，手动清除；编号不复用，以便记录里"依据工作台笔记 WN-n"的引用不会指错。
- **背景**：用户发现点"完成"后笔记就看不见了，并问笔记能否存到一个地方，让 AI 据此更新记忆或进一步与人交互。核对发现 AI 本来就能读到笔记，但没有任何说明提到它，也没有"交给 AI"的状态和回写结果的途径。
- **被放弃的方法**：

| 方法 | 问题 | 现在的处理 |
|---|---|---|
| AI 处理后直接写入，用户事后在"已处理"里查看 | 用户要求写入前先预览 | 方案预演、用户执行 |
| 用户确认后等 AI 下一轮对话再执行 | 写入的内容可能与预览不同；还要多等一轮 | 方案存在服务端，执行时原样写入 |
| 把笔记写成记忆记录 | 笔记是想法和待办，不是结论；会进入检索和复核 | 笔记留在 `.burrowl/workbench/`，结论经方案写进记录 |
| 处理完自动删除笔记 | 记录里的笔记编号会失去出处；规则要求不静默删除 | 折叠保留，用户手动清除 |
| 为批准人扩展 Actor 字段 | 改变记录契约 | Actor 仍是起草的 AI，批准写在保存原因和笔记往来里 |

- **影响与代价**：笔记文件改为 `{next_seq, notes}`，旧的列表格式可直接读取；`WorkbenchPrefs` 只保留视图偏好。跨对象的方案没有原子性，中途失败时已写入的步骤保留并如实报告。
- **实施记录**：见设计稿 §10。

| 先建完整的版本迁移框架 | 格式还没改过，迁移函数无从验证 | 第一次改格式时补"读入时转换"，由标本检验 |

### R17 后切分与嵌入模型选择（2026-10-11）

- **决定**：完整设计见 [设计稿 R17](design/R17_LATE_CHUNKING.md)（D-01 至 D-08）。
  - 向量改用后切分：整条记录一次编码，再按块或段落分别求平均。
  - 新建的数据目录默认使用中英双语的 jina-embeddings-v2-base-zh。已有数据目录不受影响，可以手动切换。
  - 保留 windows（0.5 的方式）、whole、late 三种切分方式和一套评测方法，供用户自行比较。
- **演进过程**（同一天的连续讨论，每一步修正了上一步的一部分）：
  1. **检索为什么慢**：
     - 用户问 Google 为什么在大库上也快。实测测试数据目录（20 个条目）的一次召回：SQL 检索和查询编码共几十毫秒，重排模型打分却要 2–5 秒，而且波动很大。
     - 原因是 onnxruntime 默认按 20 个逻辑核开线程，并让空闲线程忙等。在大小核混合的 CPU 上，关闭忙等后从 2.9 秒降到 0.44 秒。
     - 和 Google 的差别在于固定开销，而不是数据量：他们按命中的倒排列表计算成本，重计算都在离线完成，神经模型只用在少量候选上并跑在专用硬件上。
     - 用户决定暂不修改。
  2. **数据能否随升级保持兼容**：派生数据都可以重建，但兼容只是因为格式至今没变。为此建立了兼容性标本（见上一条"真源兼容性标本"）。
  3. **切分块是否太小**：MiniLM 的窗口正文中位 94 token；上下文信封被截到 32 token，原本要放的检索问题和定义块基本丢失；Markdown 只有标题的章节会单独成段；关联记录的全文条目是空的。
  4. **回顾 R12**：当时已确定"换长上下文模型、整条嵌入"的方向。Qwen3-0.6B-Q 单看向量通道更好，但融合后在 13 题上更差，而且慢约 17 倍、内存约 7 倍，所以暂缓，"等真实题集再测"，题集至今没建。我第一次建议时漏提了这段历史，被用户指出。
  5. **选候选模型**：
     - 第一次只按"fastembed 支持、体积、窗口大小"挑模型，没有先查公开评测，被用户指出。之后参考 C-MTEB 补上了 bge-base-zh。
     - 用户又提醒要考虑中英混用和科研场景，因此评测加入了合成题集中的中英混合类和英文科研摘要（SciFact）。
     - bge-zh 在中文上远好于 MiniLM，但在英文科研上更差，被排除。
  6. **512 与 2048**：
     - 用户指出 512 不能保证 L1 块不被切开。
     - 我改提 2048，用户追问 2048 是怎么定的，以及多个意思压进一个向量是否会过度压缩。重新统计后发现：块大多已经在 512 以内，调大上限真正影响的是记录级条目，等于把多个块合进一个向量。因此收回 2048 的建议。
  7. **长窗口还是切块**：
     - 用户引用一篇文章：切错块的损失大于直接用长窗口。
     - 讨论后的结论：那类比较针对按固定长度切块；burrowl 的块是作者写的自然边界，真正会切错的只有超长块和记录级拼接文本。
     - 后切分能同时回应两方面的担心：不丢上下文，也不过度压缩。
     - 用户决定先实现后切分（方案 C），并要求留下评测方法供以后比较。
- **实测**（详见设计稿 §7）：
  - 合成中文题集（540 题）：向量通道 MRR@10，MiniLM 0.47，jina 0.75；中英混合类 Recall@10，MiniLM 0.40，jina 1.00。
  - 浮点样例（13 题）上 jina 的名次指标低于 MiniLM；late 召回最高，但 MRR 最低。题量太小，仅作方向参考。
  - jina 在 SciFact 上的结果尚缺：fp32 版在 2 线程下估计要 2 小时编码，用户决定最后再测。
- **被放弃的方法**：

| 方法 | 问题 | 现在的处理 |
|---|---|---|
| 把窗口调到 2048，各段单独编码 | 依据只有一个块；记录级条目会把多个块压进一个向量 | 后切分：上下文长度和向量粒度分开设置 |
| 整条记录一个向量（whole） | 多个意思平均成一点，具体问题相似度下降 | 保留为评测对照组 |
| bge-small-zh / bge-base-zh 作为默认 | 英文科研明显变差；CLS 池化、512 上限，不能后切分 | 保留在模型清单中可选 |
| 把代码中的配置默认值直接改成 jina | `burrowl init` 不写配置文件，没有配置文件的旧数据目录会被悄悄换模型 | 只在新建数据目录时把 jina 写进配置 |
| 后切分时只编码区间本身 | 区间外的上下文被丢掉，等于没有后切分（真实模型测试发现：同一段文字在不同上下文中向量完全相同） | 编码窗口在预算内向两侧扩展；加测试固定 |

- **影响与代价**：
  - 新数据目录需要 jina 模型（约 640 MB），离线完整包因此增大约 0.6 GB。安装时只补齐共享目录里还没有的模型。
  - fp32 版 jina 在 2 线程 CPU 上编码约每秒 450 token，比 MiniLM 慢约 7 倍，首次建索引和大批量导入明显变慢。
  - 已有数据目录保持原模型，切换方法见设计稿 §6。
  - 检索质量的结论要等补测（SciFact、中文长记录题集），由用户用评测方法自行比较。

### R18 归属判定与阅读会话的衔接（2026-10-11）

- **决定**：完整设计见 [设计稿 R18](design/R18_ROUTE_READING.md)（D-01 至 D-06）。
  - 判定和续接是全文阅读前的预判断，不写进阅读会话。
  - 判定之后为同一需求开阅读，复用判定那一轮的召回与筛选包。
  - 先确认或新建对象，再带 `owner_id` 开阅读。
  - 关联在实际阅读、验证后由 AI 写记录时建立。
  - 新建或采用的对象立即建检索投影。
- **背景**：用户问 burrowl 认为应当新起对象、又找到若干相关对象时，新研究怎样进行、新记录是否会与相关对象建立关联。核对发现：判定只给各对象独立的筛选包；新对象与相关对象之间没有任何自动连接；判定后开阅读会重复同一次召回；阅读会话的归属只能在开始时给。
- **演进过程**：
  1. 第一轮我提了五项：新对象第一条记录必须引用候选对象（A）、把 `attribution.rejected` 转成关联候选（B）、阅读会话改绑接口（C）、判定不做综合（D）、评估加关联指标（E）。
  2. 用户指出：判定不读全文，判定结果不适合进阅读会话；第二次召回应省略；能确定的关联在建会话时定下，不能确定的每轮验证后再建，由 AI 写记录时判断。据此撤回 B 和改绑接口：判定不需要全文，阅读放在归属定下之后，会话天然有归属。
  3. 用户又指出 A 也不对：只看过筛选包或结构时的"相关"是预判断，不应强制写成引用。撤回 A。
  4. 实施时发现设计稿原写的"有缺口就不复用"多余且有害：只有业务卡的对象、没有向量模型的环境会一直有缺口，复用永远不发生；"判定 → 新建 → 开阅读"这条主要路径也必然失效。改为按"就绪对象及其索引水位"判断，缺口现算。
- **被放弃的方法**：

| 方法 | 问题 | 现在的处理 |
|---|---|---|
| 判定时直接建立阅读会话 | 判定回答"是不是同一目标"，不读全文；会话只记录围绕阅读问题的判断 | 判定只读；随后的阅读复用召回结果，判断重新做 |
| 新对象第一条记录必须引用候选对象 | 筛选包级别的"相关"不可靠 | 实际读完、验证后由 AI 判断 |
| 阅读会话改绑归属的接口 | 只有"读完才能定归属"时才需要，而判定不需要全文 | 顺序固定为先定归属再开阅读 |
| 全库检索状态的整体指纹 | 新建任何对象都会让复用失效 | 只比对就绪对象及其索引水位 |
| 有缺口的结果不留作复用 | 缺口长期存在的环境里永远不复用；同一状态本来就得到同样的缺口 | 缺口每次现算 |

  5. 实施中还发现 `memory.owner_create` / `owner_adopt` 不建索引：只有业务卡的对象在每次召回里都是 not_indexed 缺口，判定也找不到它（可能重复新建）。改为新建后立即建投影。代价是新建路径上开阅读时召回确实不同，不能复用；用户在"新建路径重新召回""先开阅读再新建并归属会话""不建索引、不算缺口"三者中选了第一种（2026-10-11）。
  6. 用真实模型走查"判定 → 新建 → 阅读 → 写记录与关联"：流程走通，新目标记录引用交接的固定引用后，图中有边连到相关对象。走查发现会话自己的新对象（只有业务卡）排在第一批最前，改为所属对象尚无记录时不进入该会话召回（D-06）；保护项报错补上缺少的项。
- **影响与代价**：多了一份进程内的派生缓存（ARCHITECTURE 状态表）。新建路径上的阅读多一次召回（约 1 s）。CLI 每次是新进程，不复用；MCP 进程内 10 分钟有效。复用判断本身要读一遍各对象 HEAD 与就绪判断，未命中时召回前后各做一次。
- **实施记录**：见设计稿 §6。

### R19 关系知识的检索与联想（2026-10-12）

- **决定**：完整设计见 [设计稿 R19](design/R19_RELATION_KNOWLEDGE.md)（D-01 至 D-12）。
  - 默认可见范围按记录类型：知识记录与关联默认全库可见，工作状态默认只在本对象可见；修订沿用原值。
  - 关系知识分成关系陈述（结论、关联，进检索）与关系指向（supports 等引用，图扩展时显示为关系线索）；结论、已采纳关联、概念页进发现投影。
  - 统一边标准；联想改为从笔记出处（锚点优先）出发、只走跨对象边的一跳图扩展，按焦点相关度取候选；扩展来的对象默认定点阅读。
  - AI 扩大检索的模糊度须经用户批准；RRF 图路线退出阅读会话；两层关系词表，超出推荐范围只给 warning。
- **背景**：R18 走查发现 AI 按默认保存的 L3 在全库召回里看不到——工作区默认可见范围是 owner_only，且没有任何规则提醒 AI。进一步核对发现：结论只进全文投影；关联写死 owner_only 且说明文字不可检索；图扩展只调整排序、不把关系交给 AI；联想策略其实是 AI 改写问题再召回；AI 面对 23 个关系名且没有按字段约束。
- **演进过程**：
  1. 先提出按记录类型设默认可见范围、关联与概念页进检索。用户追问关系图里的 claim、supports 等是否都算知识、应该放在发现投影还是图扩展里，要求统一的检索方式。
  2. 据此划分关系陈述与关系指向：有文字的进条目层，没文字的用于扩展。用户补充：联想应定义为图扩展；AI 扩大检索模糊度应由用户决定；担心边类型与属性太多 AI 和程序管不过来。由此形成统一边标准与两层词表（AI 真正需要判断的只是类别边界）；超出推荐范围只给 warning，保持 R12 D-27。
  3. 用户指出以整个对象为种子会带来大量与问题无关的弱关联，且扩展来的对象整读会让上下文爆炸。种子改为笔记出处，扩展来的对象改为定点阅读。
  4. 用户提出以阅读会话中的引用为种子。核对发现笔记出处多为整条记录、结论不能被引用、"支撑"与"值得追"混在一起，于是放宽可引用身份到块与结论，增加扩展锚点与焦点（方案 C）。
  5. 实施中修正：中转节点按引用它的不同对象数判断热门；同一对节点只取最强边；对象汇总时同一记录只计一次——三处都是样例测试暴露的重复计分。另把 input 加入推荐关系名。
- **被放弃的方法**：

| 方法 | 问题 | 现在的处理 |
|---|---|---|
| 为 supports 等关系指向单独建检索条目 | 没有自身文字，信息主体是声明它的结论或记录 | 图扩展时显示为关系线索，文字取自声明者 |
| 以整个对象为扩展种子 | 大对象里多数节点与问题无关，带来大量弱关联 | 种子取笔记出处，锚点优先 |
| 扩展来的对象整读 | 上下文成倍增长 | 默认定点阅读，按需升级 |
| 联想 = AI 写文本再召回 | 改变的是用户问题的边界 | 联想只指图扩展；扩大检索须用户批准 |
| 直接拒绝非推荐关系名 | 违反 R12 D-27，旧草案会被拒 | 只给 warning，收口时列出 |
| 按边数判断热门节点 | 同一记录多字段多边，记录与结论是不同节点，会误判 | 按引用它的不同对象数 |

  6. 真实模型走查后用户决定：块与结论种子带上所在记录（权重减半，只走入边与对称的关联边）；已有 owner_only 数据做可见范围补齐计划，由用户勾选后执行；问题记录暂不进入发现投影。
- **影响与代价**：投影版本升到 v3，已有索引需重建；新知识记录默认全库可见（已有记录由用户经补齐计划修订）；联想必须在写好笔记后才能进行，比原来靠后；阅读预算增加 graph_edges。浮点样例回归无变化，但样例对本次改动不敏感。
- **实施记录**：见设计稿 §9。

### R20 AI 填写的字段与报错（2026-10-12）

- **决定**：完整设计见 [设计稿 R20](design/R20_AI_FIELDS_AND_ERRORS.md)（D-01 至 D-10）。
  - 服务能推导的草案字段（`owner_id`、`sensitivity` 等）可以省略；契约把每个字段标为 required / optional / conditional，由 schema 与默认值表生成并用测试锁住。
  - AI 直接编写的结构化参数在工具 schema 中声明字段（记录相关的取自记录契约），复杂参数附示例；说明写在工具自己的描述里，Skill 只讲何时用与判断。
  - 参数只在 `registry.call` 校验一次，MCP 层不预校验；错误一次列全，path 从参数根算起，带允许值与下一步提示。
  - 意外异常返回 `INTERNAL_ERROR` 与 `incident_id`，堆栈进数据目录的错误日志；被拒绝的调用按工具统计（`system.tool_errors`）。
- **背景**：另一个 agent 调 `memory_commit` 得到"单批只允许一个归属对象"，无从修正。复现发现草案省略 `owner_id`（它与请求顶层重复）和写错对象报同一个错，path 还指向请求顶层；这条要求只出现在 `memory_contract` 的返回里，契约示例写的又是另一个对象。进一步核对：契约把 `change_reason` 列为"不要写"而服务在修订时要求它；`sensitivity` 说明写"默认"却是必填；15 个结构化参数只是裸对象；MCP SDK 先按签名预校验，返回 pydantic 英文原文，根本到不了统一的错误转换。
- **外部参考**：MCP 2025-11-25 规范把输入校验错误归为工具执行错误、要求给出可执行的反馈；Anthropic 的工具设计建议（描述最重要、严格数据模型、报错给改法与正确格式示例、按参数错误次数改说明）；复杂参数示例在 Anthropic 内部测试中把正确率从 72% 提到 90%；OpenAI 的"应用已知的值不要让模型填"。strict 模式由调用模型的客户端开启，服务端只能把 schema 写严格并始终自己校验。来源链接见设计稿 §3.1。
- **被放弃的方法**：

| 方法 | 问题 | 现在的处理 |
|---|---|---|
| 强制"先调 `memory_contract` 才能提交" | 服务要追踪调用顺序，且仍挡不住照抄示例出错 | 就近说明 + 报错指向契约 |
| 把整份记录 schema 塞进 `memory_commit` 的参数 schema | 随 kind 变化、体积大 | 草案在参数 schema 中只是"对象 + 说明"，字段按需查契约 |
| 为结构化参数另写一套 pydantic 模型 | 与记录契约重复，两处会漂移 | 形状直接引用记录契约，发布与校验用同一份 schema |
| 把堆栈返回给 AI | 占上下文、AI 改不了，可能带出内部路径 | 只给类型、摘要和 incident_id，堆栈进日志 |

- **影响与代价**：校验消息全部改为中文并带允许值，不再有测试依赖英文原文；契约输出新增 `fill`、`default`、`do_not_write`、`payload_legend`；`memory_summary_save` 修订时 `record_id` 与 `expected_revision` 必须一起给；工作台方案的步骤也接受 MCP 工具名。MCP 适配层依赖 SDK 内部的工具注册对象。
- **实施记录**：见设计稿 §7。

### R21 外部资料导入不丢细节、引用可读可跳转、工作台后台运行（2026-10-12）

- **决定**：完整设计见 [设计稿 R21](design/R21_FAITHFUL_IMPORT.md)（D-01 至 D-15）。
  - L0–L4 写成"信息分级"的本质原则：按内容片段回答的问题落层（L1 具体是怎样的、L2 怎么走到这里、L3 以后怎么用、L4 是什么/到了哪一步/能做什么/接下来做什么），L1 是无损层，L2–L4 提炼并就近链接 L1；拿不准时偏向保全。常用类型的划分作为默认示例，不是模板。
  - 兜底分层：规则内的不对称默认、导入的覆盖报告（原文快照逐段对比 L1）、原件分段的检索、收口清单（`unlinked_details`）、工作台"原文展开"加笔记交给 AI。
  - L1 新增可选 `origin`（原件 + 分段）与 `unit_type=general`；原文中的实验可用 `origin` 代替 `run_ref`；L0 新增可选 `omitted`。
  - 导入时保存原文快照（只存抽取的文本，不存原件），图片经 `sources_attach` 复制为数据目录内的附件；原件变化后按快照逐段对比，维护计划指出受影响的 L1 与分段。
  - 正文中新写入的长编号（`MEM-<uuid>` 等）或指纹直接拒绝并给出替换写法；已有记录由维护页"引用改写"机械替换，不调用 AI。工作台的来源、链接、正文 `[[…]]` 都可点击跳转。
  - 工作台后台运行：`burrowl start / open / stop / restart / status`，网址固定，进程名 burrowl-workbench，首页可重启加载新版本；开始菜单快捷方式（不写注册表），不做开机自启。
- **背景**：用户导入一篇核心算法文档后，L4 归纳正确，L1 却也做了大量归纳；图片没有引用；L4 没有链接任何 L1；工作台点不开引用。核对后发现：规则从未要求 L1 保留原文细节（导入步骤只写"方法、定义、计算写 L1"，L1 的写法以实验报告为模板）；`figures` 只接受数据目录内的附件，却没有任何工具能把图片放进去；外部资料里的实验写不成实验类 L1；原件只存指纹，变了无从比较。
- **被放弃的方法**：

| 方法 | 问题 | 现在的处理 |
|---|---|---|
| 让 AI 先判断整篇文档的类型，再按类型模板填写 | 文档常常穿插多种形态，类型无法穷举 | 按内容片段判断落层，类型表只作默认示例 |
| 提交时检查"L4 是否引用了下层" | 指标不治本，覆盖情形少 | 就近链接写进原则；收口时列出没被指向的 L1 |
| 保存原件副本以便对比 | 检索基于转写的记录，原件副本只是负担 | 只保存抽取的文本快照，原件随备份打包 |
| 拿新原件与 AI 写的记录比较来找变化 | 两种写法差异大，假差异多，还要调用 AI | 新旧快照按内容逐段对比，确定性的 |
| 展开稿保存为文稿记录 | AI 要多维护一份文稿，且会与 L1 脱节 | 按 `origin` 现算的视图 |
| 提交时拦截所有长编号 | 旧记录的任何修订（包括程序生成的）都会被卡住 | 只拦新写入的；旧的经"引用改写"计划处理 |

- **影响与代价**：记录契约增加可选字段，按"旧数据永远可读"冻结新的兼容标本；数据目录新增 `attachments/`、`.burrowl/snapshots/`、`.burrowl/server.json`；覆盖报告阈值没有真实数据依据；新增工作台专用操作组 `ui`、`server`（不在 MCP 默认工具组）。
- **实施记录**：见设计稿 §8。

### R22 删除记录与对象（2026-10-13）

- **决定**：完整设计见 [设计稿 R22](design/R22_DELETION.md)（D-01 至 D-12）。
  - 区分撤回与删除：撤回是"曾被当真、后来发现错了"，要保留；删除是"本来就不该记"（测试数据、重复、写错对象），不应再出现在任何视图。
  - 删除记录用墓碑提交：新提交从 `record_heads` 移除记录，原指针存进 `removed_records`；旧修订、固定引用、提交链指纹都不变，恢复就是把原指针放回。
  - 删除对象沿用 Run 回收站：整个对象目录（被采用文档只移记忆目录）移到 `.burrowl/trash/owners/`，可恢复，清空仅限用户。
  - 都有引用护栏：其他记录的当前修订还在引用时拒绝并列出引用者，不做级联删除。
  - AI 也能删除到回收站（用户决定），必须写理由。
- **背景**：用户发现误建的对象、测试记录没有办法去掉，只能撤回后一直留在列表、检索和文稿里。
- **被放弃的方法**：

| 方法 | 问题 | 现在的处理 |
|---|---|---|
| 物理抹除单条记录 | 要重写提交链和指纹，已有固定引用失效，违反"旧数据永远可读" | 墓碑提交；要彻底清除就删除整个对象并清空回收站 |
| 删除时级联删除引用者或自动改写引用 | 会悄悄改动别人的结论与依据 | 拒绝并列出引用者，由 AI 或用户处理 |
| 删除只在工作台提供 | AI 整理时发现的测试数据也要用户手动清理 | AI 可删到回收站；清空仍仅限用户 |

- **影响与代价**：提交清单增加三个可选字段（只在用到时写入）；数据目录新增 `.burrowl/trash/owners/` 与回收站日志；关键操作记录增加 `remove` 类型；对象删除与另一进程的提交之间只靠写锁文件与 HEAD 核对，没有跨进程的原子性（本地单用户场景）。
- **实施记录**：见设计稿 §8。

### R23 结论的结构（2026-10-13）

- **决定**：完整设计见 [设计稿 R23](design/R23_CLAIM_STRUCTURE.md)（D-01 至 D-18）。
  - 结论分三层：核心（谓词＋参与者）、限定（框架中的可选角色与适用范围）、依据；判断规则是"去掉后意思变了属于核心或限定，只是更难相信属于依据"。
  - 存储用多元参与者，角色由谓词框架预先定义；二元读法推导得出，不另存。
  - 结构是 AI 自动生成的标注，不计入内容指纹；陈述、适用范围、依据是权威内容，用户遇到不对时对照陈述核验。
  - 边类别重整为结构、依据、引用、关联、提及、结论要素；删除快捷边，只用节点模式展示；图扩展经过结论，关系窗口带出陈述与适用范围。
  - 概念链接改为投影时解析，先写名、后建页可以自动接上。
- **背景**：用户检查关系图时发现分类混乱：`concept` 类别混着"提到"与"在结论中的角色"，快捷边与结论节点是同一份知识的两种画法；讨论中又发现只能表达二元关系、修正结构会让复核失效、`contradicts` 有两种写法、依据边没有文字。
- **被放弃的方法**：

| 方法 | 问题 | 现在的处理 |
|---|---|---|
| 只把类别改名（"概念提及与角色""结论陈述"） | 没有解决两种含义混在一类、同一结论画两次 | 按"边表达什么"重分类别（D-11） |
| 结论节点与快捷边二选一的"连线模式" | 两种表达要维护两套规则；快捷边脱离条件，导出与扩展时容易被当成无条件成立 | 只用节点模式；扩展经结论中转，条件随窗口带出（D-14） |
| 参与者＋每条临时命名的自由角色 | 同一关系的角色名对不上，查询要先猜角色名 | 角色由谓词框架定义，框架外用 `x-`（D-04） |
| 二元主谓宾＋限定符（Wikidata、Biolink 的主流写法） | 把"哪两个是核心"写进存储，对称关系与多个同等参与者要硬分主次；用户强调本系统首先是完整记录关键信息的数据库 | 存储多元，二元读法由框架推导 |
| 结构计入指纹、每条人工确认 | 数据多时核对负担过重，且修正结构会让复核失效 | 结构不计入指纹，默认自动生成（D-02） |
| 保留旧 `relation` 的读取路径 | 现有标本与样例中没有 `relation`，用户数据目录清空重建，兼容层没有对象 | 直接替换（D-16） |

- **实施中发现**：结构不计入内容指纹后，提交服务原先按内容指纹判断"没有变化"，会把只改结构的修订静默丢弃；改为同时比较完整内容。凡是把某些字段移出指纹，都要检查所有用指纹判断"相同"的地方。
- **影响与代价**：图投影版本升到 graph-v3，交换格式版本递增；内容指纹的定义改变（只影响带 `relation` 的记录，现有标本不受影响）；投影水位要包含概念库指纹；结论要素边的扩展权重需要用评测确定。
- **实施记录**：见设计稿 §8。

| E2（2026-10-08） | 迁移核对发现阅读会话丢失了若干源项目的程序规则：来源固定与陈旧检查、读完才能写笔记、quick 逐片段采纳、全文补偿前提 | 重构时，AI 依赖的程序规则要逐条列出并配测试，不能只迁移"主流程" | 已修复并加测试；MIGRATION_AUDIT C 节 |

| E4（源项目） | 软件回归通过，但检索留出题集质量不达标 | 能运行不等于找得准；检索方案需要独立的质量、延迟和上下文成本证据 | 浮点样例小题集已建（R12 T-P0.2）；真实数据题集待用户抽查 |

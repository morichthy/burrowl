# 记录标准：怎样写 L0–L4、文稿和结论

写任何记忆记录前读本页；具体字段用 `memory_contract(kind)` 查（会返回经过校验的示例草案）。术语定义见 [GLOSSARY](../docs/GLOSSARY.md)。

## 1. 层级的本质：信息分级，细节不丢

L0–L4 是**内容压缩与展开的层级**：L1 不压缩，L3 压缩到"仍能直接使用"，L4 只留入口所需的要点。层级同时决定检索时的"发现面"：

- L4 和 L3 的正文、L2 的摘要、L1 的检索说明，会进入全库发现索引；
- L1 的完整正文、文稿和 L0 原件，要在完整阅读时才读到。所以 **L4 写不好，别人就找不到这个对象**；L1 写潦草了，细节就永远丢了。

层级只表示内容职责，不表示可信程度，也不是必须逐级完成的流水线：缺层是正常的；小操作可以不写记录；内容很短时可以只有一条 L4，它的正文就是完整内容。**预期会被其他任务检索、续接或引用的对象，至少维护一条当前的 L4。**

文档和工作的形态无法穷举：一篇材料可能一会儿是论文、一会儿是随笔、一会儿是实验说明，交互中产生的内容也一样。**不按文档类型套模板，而是逐段判断这段内容回答哪个问题**，按下面的原则落层。第 3 节的两张表是常见情形的默认划分，帮助不走偏；遇到表里没有或混合的形态，回到这里的原则判断。

**原则 1：每层回答一个问题。**

| 层 | 回答的问题 | 一句话 |
|---|---|---|
| L0 | 依据是什么、在哪里 | 原件登记，只读 |
| L1 | 具体是怎样的？ | 能复核的细节，完整保留 |
| L2 | 是怎么走到这里的？ | 实际发生或原文记载的过程 |
| L3 | 以后遇到类似问题该怎么用？ | 一切可能复用的经验，逐条带条件和反例 |
| L4 | 这是什么，现在到了哪一步，能用来做什么，接下来做什么？ | 对象的入口与当前状态 |

- **L0 依据**：原件（文档、数据、代码、日志）的登记说明：是什么、谁或哪次执行产生、针对什么问题、版本、怎么解释（列、单位、坐标）、有哪些限制；导入时有意省略的原文段落及理由（`omitted`）。不转述原件内容（那是 L1）；没读过的原件不能声称已核验全文。
- **L1 细节：具体是怎样的**。读者要复核、复算、复现或照着做时需要的一切：定义、公式与推导步骤、算法步骤与接口、参数与取值理由、实验设置与工况、结果表、图与图注、代码与命令、例子、原文的论证与观点原话、限制条件。
  - 导入资料：保留原文中所有有用的内容，接近原文表述，按原文顺序；AI 的解释单独成块并标"整理者注"。
  - AI 研究交互：本次实际做了什么、怎么做、得到什么，写到别人能复算的程度；对话结束后这里是唯一完整的记录。
  - 不写对多条细节的归纳评价（写 L3 / L4），不编没有发生的过程。
- **L2 经过：是怎么走到这里的**。起点与背景 → 按实际顺序的尝试、选择及理由、观察到的现象与失败、认识如何改变 → 当时还没解决的问题；写明来源是原文记载、本次工作还是事后补写。导入资料只在原文写了形成过程（版本演进、排错经过、讨论纪要）时才写；只做了一步就如实写一步。结果细节引用 L1，不复述。
- **L3 经验：以后遇到类似问题该怎么用**。**只要以后可能用得上的经验都留下**，不因为"太小""只遇到一次"而丢掉；一条经验一条记录或一个结论。每条写清：在什么问题和条件下、观察或结论是什么、怎么用、为什么有依据（链接 L1）、已知反例、不能推广到哪里。方法经验、失败与反例、参数和工况边界、工具或数据的特点、偶然发现都算。假设要写验证条件，建议不冒充实测。导入资料中原文明确的主张写成 L3 并标"原文主张"，AI 自己的评价另写。L3 是细化的、能单独检索到的经验，L4 只点名其中最关键的几条。
- **L4 概览：这是什么，现在到了哪一步，能用来做什么，接下来做什么**。对象的用途和问题边界；主要方法或内容；**已经有了哪些关键结论**（点名并链接 L1 / L3 / 结论）；**关键反例与限制**；当前状态；**下一步建议做什么**、还有哪些未决问题。不展开下层也能知道"它是什么、现在能用来做什么、继续做应该从哪里开始"。导入资料时写材料讲什么、能做什么、适用边界、主要内容的结构（链接到对应的 L1），下一步可以是"还有哪些部分未导入或未核实"。不复述细节，每个关键结论、数字、方法都就近链接下层。

同一段原文可以同时贡献给多层：例如随笔中的一段经验，原话保留在 L1，提炼出的判断写进 L3 并链接那个 L1 块，其中最关键的一条再由 L4 点名。

**原则 2：保全。** 任何**会消失或不会被检索读到**的有用细节，必须完整落在 L1。导入外部资料时原文就是来源（原件只登记，不进记忆正文，检索读不到原文的结构）；AI 交互中的工作，对话和执行过程就是来源，对话结束就消失。

**原则 3：先保全，再提炼。** 先写 L1，再写 L2–L4。上层写到关键事实、数字、方法时，就近用 `[[@记录]]` 或 `[[@记录#块]]` 链接对应的 L1（链接到块就够了，不要求逐句）。收口时 `memory_consolidate_prepare` 的 `unlinked_details` 会列出没有被任何上层指向的 L1。

**原则 4：出处分开。** 原文的内容、本次工作的观察、AI 的推断分开写明。原文给出的结果可以写成 fact 类结论，依据指向原文出处，但不算已复核。

**原则 5：组织顺序是默认值，独立可读才是要求。** 转写原文默认按原文顺序，开头写一小段上下文（在原文的位置、依赖什么）；本次工作产生的技术单元默认按第 4 节的"问题 → 方法 → 结果 → 限制 → 复算依据"。两种都不强制，但都必须满足第 2 节"只看这一条也能读懂"。

**原则 6：拿不准时偏向保全。**

- 拿不准有没有用：保留。
- 拿不准放哪一层：放 L1。细节层不会丢，以后可以再从 L1 提炼上层；压缩掉的细节找不回来。
- 拿不准 `unit_type`：用 `general`。
- 只省略能确定没有用的内容（目录、版权页、致谢、重复的页眉页脚、与主题无关的套话），并在 L0 的 `omitted` 登记省略了哪里、为什么。

| 层 | 类型（kind） | 正文写在哪 | 关键结构字段 |
|---|---|---|---|
| L0 | source | `body_markdown`：登记说明 | `source_ref`（先 `sources_register`）、`acquisition`、`completeness`、`omitted` |
| L1 | detail | **`payload.blocks`**；`body_markdown` 必须是空字符串 | `unit_type`、`run_ref`、`origin`、`retrieval_description`、`blocks`、`figures`、`claims`（只限 fact / calculation） |
| L2 | narrative | `body_markdown` | `question`、`stages[]`、`limitations`、`claims` |
| L3 | experience | `body_markdown` | `problem_structure`、`recommendation`、`applicable`、`prohibited`、`failure_modes`、`knowledge_type`、`claims` |
| L4 | overview | `body_markdown` | `question`、`methods`、`results`、`current_stage`、`limitations`、`open_questions` |
| — | document / document_section | 章节的 `blocks`（prose 文字或 unit 技术块） | 文稿根：`document_type`、`section_refs` |

**L2–L4 的正文必须写在 `body_markdown`**：读者和检索都读正文，不会把 payload 拼回正文。不能把背景、结果、限制只放在 payload 里。

## 2. 每条记录必须独立可读

读者只拿到**这一条的正文**（L1 包括它声明依赖的定义块），不读聊天、相邻记录或整篇文稿，也要能回答这几个问题：

- 对象是什么，为什么记这一条；
- 在什么条件下做了什么，得到了什么；
- 什么时候不能用。

规则：

- 关键术语第一次出现时解释；公式给出变量、单位、初值和成立条件；比较要写明对象、输入和评价基准。
- 不写"同上""见上一轮"，也不用记录 ID 或附件链接代替解释。
- 未知的背景或依据明确写成缺口。未完成的内容可以保存，但不能称为可直接复用的完整经验。

| 层 | 本条至少要让读者理解 |
|---|---|
| L0 | 材料是什么、谁或哪次执行产生、针对什么问题、版本和输入条件、怎么解释（列、坐标、单位、限制）。原件只读；没展开读过的原件不能声称核验了全文 |
| L1 | 问题与范围、输入与方法、必要定义和公式、主要结果、限制、复算依据（转写原文时：在原文的位置与上下文，以及原文的全部有用细节）。结果块必须用 `requires_block_ids` 带上它依赖的定义块 |
| L2 | 背景和起点 → 本条记录的实际尝试、选择理由、观察或失败、认识变化 → 简单结论和未解决的问题。只发生了一步就如实写一步，不编造多轮演进；写明是原文记载、本次工作还是事后补写 |
| L3 | 在什么问题和条件下，有什么观察、结论、假设或建议；怎样使用、为什么有依据、关键反例、不能推广到哪里。假设要保留验证条件，建议不冒充实测 |
| L4 | 对象的用途和问题边界、主要方法或内容、已有的关键结论与证据强度、关键反例与限制、当前状态、下一步建议与未决事项。不展开下层也能知道"它是什么、现在能用来做什么、接下来做什么" |

**写完后在同一次任务中逐条做脱离上下文的回读**：只看这一条，检查上面的问题能否回答，缺了先补再提交。这个自查不产生任何"已确认"状态，结构校验通过也不等于内容充分。

## 3. 默认划分：常见情形怎样落层

以下是默认划分，帮助不走偏，不是规定。遇到表里没有、或几种形态穿插的材料，按第 1 节的原则逐段判断。

**表 A：常见内容片段落在哪里**

| 内容片段 | 落在哪里 |
|---|---|
| 定义、符号表、方程、算法步骤、伪代码、接口说明 | L1（`method`），定义单独成块供依赖 |
| 推导过程 | L1（`derivation`），每一步保留，变量与成立条件写全 |
| 实验设置、工况、样本、结果表、误差 | L1（`experiment`；本次执行用 `run_ref`，原文中的实验用 `origin`）；大数组留在 L0，L1 写明怎样引用 |
| 数据分析、对比、评测 | L1（`analysis`） |
| 图与图注 | 图片用 `sources_attach` 放进附件，L1 在原位置用 `![图注](figure:序号)` 引用并照录图注 |
| 表格 | 转成 Markdown 表格保留在 L1；太大的留在 L0，在 L1 写清列含义和引用位置 |
| 代码片段、命令、配置 | L1，原样保留，写明版本与环境 |
| 原文的观点、讨论、随想 | 原话保留在 L1（`general`）；能复用的判断另写 L3 并标"原文主张" |
| 经验、教训、注意事项、反例 | L3，每条带条件与反例；原文或本次的 L1 作为依据 |
| 版本演进、排错经过、会议讨论与决定 | L2（只写实际发生或原文记载的），细节链接 L1 |
| 摘要、引言、结论段 | 帮助写 L4；原文的结论原话同时保留在 L1 |
| 目录、版权页、致谢、页眉页脚、重复内容 | 省略，在 L0 的 `omitted` 登记 |
| 识别不了的扫描页、公式图片、看不清的图 | 写成缺口，不猜 |

**表 B：常用类型的划分**

| 类型 | L0 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|---|
| 核心算法 / 算法介绍 | 公司定义文档、实现版本 | 按模块：方程、符号、步骤、接口、参数表、伪代码、数值处理 | 文档记载的版本演进或排错 | 适用域、参数选取经验、已知失效情形 | 算法用途、输入输出、适用边界、模块结构 |
| 实验报告 / 实验数据 | 原始数据、实验记录 | 每组条件一个单元：目的、设置、工况、结果表与图、误差 | 实验的实际顺序与调整 | 由结果得出的有条件结论、异常与反例 | 实验目的、关键结果、限制、待补实验 |
| 科研论文 | 论文原件 | 按章节：问题、方法、推导、实验设置与结果、讨论原文 | 一般不写 | 论文主张（标"原文主张"）与本次评价分开 | 问题、贡献、关键结论、局限、与本工作的关系 |
| 公式推导笔记 | 原稿 | 每段推导一个单元，步骤完整 | 推导走过的弯路（如有记载） | 推导成立的条件、常见错误 | 推导目标与结论 |
| 随笔 / 经验帖 / 内部说明 | 原文 | 有实质内容的段落原话保留（`general`） | 文中讲述的经历 | 每条经验、教训一条 | 主题、主要观点、适用场景 |
| 会议纪要 / 讨论记录 | 纪要原件 | 每个议题的事实、数据、方案细节 | 讨论经过与决定理由 | 形成的共识与约束 | 议题、决定、待办与负责人 |
| 幻灯片 | 原件 | 每页的讲解文字与图（附件），按页 | — | 讲者的经验与建议 | 主题与结构 |
| 工具 / 数据说明 | 版本化的工具或数据 | 用法、参数、字段定义、处理流程、示例 | 选型或治理经过 | 使用陷阱、兼容性边界 | 用途、接口、数据范围 |
| AI 研究交互（本次工作） | 本次的 Run、输入数据 | 实际做法、计算、结果，可复算 | 实际的尝试、取舍、失败 | 一切可迁移的认识与教训 | 研究问题、关键结论与证据强度、关键反例、当前状态、下一步建议 |
| 排错 / 调试过程 | 日志、报错、版本 | 复现步骤、根因分析、修复方法 | 排查经过（试过什么、排除了什么） | 症状 → 原因 → 处理的经验 | 问题、根因、修复状态、遗留风险 |

**按对象类型**（同一套层级用于不同对象）：

| 对象 | 可以按 L0 → L1 → L2 → L3 → L4 组织的内容（按需选取） |
|---|---|
| research / project | 研究或交付依据 → 方法、分析、实验 → 实际探索与取舍 → 有条件的认识 → 问题和成果概览 |
| core-algorithm | 公司定义文档与实现版本 → 方程、接口、推导、验证 → 文档记载或本次的演进与排错 → 适用域和工程经验 → 算法用途与边界 |
| knowledge | 原文及出处 → 原文的方法或推导 → 原文明确写出的形成过程（**原文没写就不编 L2**） → 区分原文主张与本次认识 → 主题、用途和边界 |
| tool / data | 版本化的工具或数据登记 → 使用方法、处理与分析 → 排错、选择或治理经过 → 复用条件和失败经验 → 用途、接口或数据范围 |
| report | 报告依据 → 分析方法 → 有意义的取舍 → 限定范围的认识 → 目标、结果和限制 |

Run 不是知识对象，不写记录：执行的输入输出是证据，写在引用它的对象里（L1 实验用 `run_ref`，L2 的 stage 用 `evidence_refs`）。Run 日志不能代替 L2，执行成功不代表结论成立。

- 一个事实只有一个权威归属，其他对象用固定引用，不复制。
- 形成记录时，除了主体目标，还要检查过程中出现的可迁移方法、失败与反例、版本/参数/工况限制、工具或数据特征、偶然发现：能独立复用的写 L3，方法和计算细节写 L1。

## 4. L1 技术单元怎么写

- `unit_type`：experiment / method / derivation / analysis / general（不属于前四类的内容，如说明、观点、经验叙述的原话）。**experiment 必须用 `run_ref` 绑定真实 Run，或用 `origin` 指向原文出处**（转写外部资料中的实验）；其他类型 `run_ref` 为 null，但仍要给出固定依据或写明缺口。不要为了凑字段虚构 Run。
- `origin`（转写外部原件时写）：`{source_ref: 原件的固定引用, locators: [原件分段的 key]}`；块上也可以写 `locators` 细到块。分段 key 取自 `sources_snapshot`。覆盖报告、原文展开、原件变化后的逐段对比都靠它找到这条记录。
- `retrieval_description`：question、method、key_findings[]、applicable[]、not_applicable[]、limitations[]。它只用于发现候选，**不是正文**。
- `blocks`：每块有稳定的 `block_id`、`role`（definitions / methods / inputs / derivation / results / discussion / limitations / appendix / introduction）、`markdown` 和 `requires_block_ids`。
- `figures`：`[{caption, ref}]`，ref 是数据目录内附件的固定引用（原件里的图用 `sources_attach` 复制得到）；块正文用 `![图注](figure:序号)` 在原位置引用。
- **拆分**：一个技术单元围绕一个问题或方法；转写原文时按原文的章节结构切，一节讲一件事就成一个单元，某节太长时按条件不同、能各自复用的界线再拆。
- **结论**：实验事实和计算结果可以直接写成 L1 的 `claims`（kind 只能是 fact 或 calculation），用 `block_id` 指向给出结果的块。推断和建议写在 L2–L4。

**本次工作产生的技术单元**，默认按读者能独立复核的顺序组织，短小节可以合并，但不能只留题目、总评和附件链接：

1. **问题与范围**：检验什么，为什么要做，比较对象和可证伪条件。
2. **输入与方法**：关键参数、单位、取值理由、样本量、随机种子、假设、程序与环境。完整数组放 L0，影响结论的参数写在正文。
3. **公式与计算**：公式、变量定义、可核验的推导步骤；写可公开复核的解释，不写模型的私有思考过程。
4. **结果**：结果表、图与图注（坐标、单位、误差定义）。图引用固定附件。
5. **讨论与限制**：观察、反例、失败类别、适用范围、不能推出的结论、下一步问题。
6. **证据与复算**：Run ID、来源 ID、版本和指纹、实际脚本和命令。没执行的计算标为推导或建议。

**转写外部原文的技术单元**，默认按原文顺序：开头一块写上下文（在原文哪一节、讲什么、依赖哪些定义），然后接近原文保留全部有用细节（公式、表格、参数、步骤、例子、论证）；AI 的解释单独成块标"整理者注"。不要把原文再归纳一遍代替原文。

示例：浮点误差要区分"精确实数输入"和"已表示为 binary64 的输入"。
$S_{\mathrm{ref}}=\sum_i \operatorname{Fraction}(x_i)$，$e_{\mathrm{abs}}=|\operatorname{Fraction}(\widehat S)-S_{\mathrm{ref}}|$。
其中 $x_i$ 是程序实际收到的浮点数，无量纲。其他研究要写自己的量纲和基准，不能照搬。

## 5. 结论（claim）怎么写

需要被复核、被正式引用的判断写进 `payload.claims`（L1 只写 fact / calculation，L2–L4 不限），每条包含：

- `claim_id`：全库唯一，建议 `CLM-<对象>-<短名>`。
- `statement`：一句可判断真假、能被单独读懂的话：主体、条件、结果都写出来，例如"在有限 binary64、存在大数抵消的输入下，补偿求和仍可能丢失小量"。不写"如上所述""该方法"这类依赖上下文的指代——结论会被单独检索到。
- `kind`：fact / calculation / inference / recommendation。
- `scope`：适用范围，也是条件的权威写法。需要被引用、比较的工况写成链接，例如"在 [[工况-满载]] 下"，图上会生成一条"条件"边。
- `evidence_refs`：依据的固定引用。relation 只用 supports（能证明）、contradicts（是反例）、input（作为输入的数据）。引用可带 `note`，写这份材料的哪部分、怎样支持或反驳；**反例（contradicts）必须写 note**，否则提交返回 `EVIDENCE_NOTE_MISSING` warning。

判断一项内容放哪里：**去掉它之后结论的意思变了，它属于陈述、参与者或适用范围；只是结论更难让人相信，它属于依据。**

- 可选 `relation`：结论的结构标注，**陈述与 scope 才是权威内容**。能看出谓词与参与者时顺手写，拿不准就不写。它不计入复核指纹：以后发现结构标错，对照陈述只改 `relation`，原复核不失效。写法：

  ```
  {predicate: "causes", negated: false（可选）, participants: [
    {role: "cause", value: "[[温漂|温度漂移]]"}, {role: "cause", value: "[[基准电压噪声]]"},
    {role: "effect", value: "高负载下的瞬态误差"}]}
  ```

  - 角色由谓词决定（`memory_contract` 的 `claim_relation.frames` 列出每个谓词的必填与可选角色）：improves / degrades（作用方、作用对象，可选基准、指标）、causes（原因、结果，可选机制）、prevents、fails_on（方法、失效情形）、applies_to、requires、equivalent_to（≥2 个比较项）、part_of。框架外的角色与自定义谓词以 `x-` 开头。
  - **共同作用就让同一角色出现多次**，不要拆成多条二元结论：拆开可能变成两个都不成立的判断。
  - 参与者能当成"一个东西"的写链接，概念页还没建也照写 `[[名字]]`（收口时建页后自动接上）；只是描述性短语写纯文字。
  - 条件写在 scope，不是角色；矛盾写进 `evidence_refs`（contradicts）或复核，不是谓词。否定结论写 `negated: true`。
- **scope 要具体**。"有限 binary64 输入、存在大数抵消"是好的；"一般情况下""大多数场景"不是范围。复核时确认的范围必须与 scope 一致。
- 改了结论或所在记录的正文，原复核会自动失效，需要重新复核。
- 成熟度（设想 / 初步 / 重复验证 / 已确立）随复核登记，不写在结论里；谁可以登记见 RULES 第 4 节。

## 6. 引用与三种关系

所有正文在事实、公式、结果和关键判断旁**就近引用**固定依据，并与 `sources` 对应。历史记录没有具体位置时，如实写缺口，不按来源顺序猜。L2–L4 写到关键事实、数字、方法时，就近链接给出细节的 L1（第 1 节原则 3）。

三种关系分开维护，不能互相冒充：

| 关系 | 用什么表达 | 含义 |
|---|---|---|
| 展开 / 组成 | `process_refs`（指向 L2）、`technical_refs`（L1）、`experience_refs`（L3）；章节的 `unit` 块；文稿的 `section_refs` | 怎样从概括展开到细节 |
| 证据 | 引用的 `relation` 为 supports、input、contradicts；claim 的 `evidence_refs` | 判断依据什么成立或被反驳 |
| 导航 | association 记录（related_to、same_problem、same_failure_mode、analogous_to），用 `relations_decide` 保存，带 `certainty`（speculative / plausible / supported） | 相似、对照、可能迁移；**不是证据** |

相似度、同一对象、阅读线索都不能自动变成 supports 或复核。"值得放在一起看"写成关联；"A 会影响 B"这类可以验证的判断写成结论（kind=inference），再链接两端。怎样按判断问题选关系见 RULES 第 6 节。

**关系名只用这几个**（按写在哪里；其他关系名仍可读取，但提交和 dry_run 会返回 `RELATION_NOT_RECOMMENDED` warning，收口时会被列出）：

| 写在哪里 | 可选 | 默认 |
|---|---|---|
| 结论、L2 阶段的 `evidence_refs` | supports、contradicts、input | supports |
| 记录的 `sources` 与 payload 中其他固定引用 | supports、contradicts、input、references | references |
| 关联的 `relation` | related_to、same_problem、same_failure_mode、analogous_to | related_to |
| 结论的 `relation.predicate` | 谓词框架：improves、degrades、causes、prevents、fails_on、applies_to、requires、equivalent_to、part_of，或以 `x-` 开头自定义 | — |
| 正文链接、结构关系（归属、包含、块依赖） | 程序决定，不用选 | — |

收到 warning 时改用推荐的关系名；确有理由保留时，在 `record_reason` 或 `change_reason` 中写明。

**关联的说明要能被单独读懂**（关联会进入检索，被其他项目直接搜到）：

- `explanation` 写清"为什么值得一起看"，并点明两端各自是什么，例如"两者都在长记录上比较切分方式：A 是方案讨论（未实测），B 是评测题集与实测结果"。不要只写"相关""参考"。
- 确定度：只凭标题或印象 → speculative；读过两端、能说清共同点 → plausible；有材料直接支持这一联系 → supported。
- analogous_to 必须写 `shared_structure`（共同的问题结构）和 `transfer_limits`（不能迁移的边界）。

**正文链接**（知识节点之间的可读链接，提交时由服务解析并固定版本，写进记录的 `links`；正文里不出现 ID 或哈希）：

| 写法 | 指向 |
|---|---|
| `[[补偿求和]]` | 概念库里的概念（按标题或别名匹配；找不到不阻塞提交，会列为缺口） |
| `[[@第三轮实验]]`、`[[@浮点求和/第三轮实验]]` | 本对象或其他对象的记录（按 `handle`，斜杠前是对象短名） |
| `[[@第三轮实验#kahan]]` | L1 记录中的块 |
| `[[!补偿抵消失效]]` | 结论（claim_id 的短名部分） |
| `[[…\|显示文字]]` | 竖线后是显示文字 |

- 记录、块、结论链接解析不了时提交失败（`UNRESOLVED_LINK`），错误里给出候选，改写后再提交。
- 正文（L1–L4、文稿章节、结论陈述）里写了服务生成的长编号（如 `MEM-<uuid>`、`SRC-<uuid>`）或 64 位指纹时提交失败（`UNREADABLE_REF`），错误的 `hint` 给出可以直接替换的短名链接；原件写成登记它的 L0 记录的 `[[@短名]]`。代码块和行内代码里的不检查。
- 修订时没改动的链接保持原来固定的版本；要指向目标的新版本，在操作里加 `repin: true`。
- 链接是导航和引用，不是证据；证据仍然写在 `sources` / `evidence_refs`。
- 链接哪些概念：L4 链接对象涉及的主要概念，L3 链接问题结构和失败模式涉及的概念，L1、L2 按需链接；结论陈述里也可以写链接。

**固定引用怎样拿**：

- 刚保存的记录：直接用提交回执里的 `fixed_ref`。
- 已有记录：用 `memory_inspect` 取 revision 和 record_hash。
- 文件：用 `sources_list` 里登记的 sha256。

不要手抄或猜指纹。

## 7. 保存顺序与回读

1. **先保存被引用的内容**（L0 → L1 → L2 → L3），再保存引用它们的概览、章节，最后保存文稿根。同一批提交里，可以用 `{client_key: "x"}` 引用同批新建的记录。
2. 用 `memory_commit`（可先 `dry_run`）提交，带上 `expected_head` 和 `request_id`：
   - 新建：`{op: "put_record", client_key, draft}`；
   - 修订：`{op: "put_record", record_id, expected_revision, draft}`，draft 是完整的新内容，并写 `change_reason`（为什么改）。
   - 草案必须写 kind、title、body_markdown、payload、sources、record_reason；`owner_id`、`sensitivity`、`discovery`、`keywords`、`provenance_gap`、`handle` 可以不写（服务补上，修订时沿用原值）。`memory_contract(kind)` 的 `draft_fields` 逐项标了 required / optional / conditional。
3. 看回执：`save_status` 和 `index_status` 是两件事。索引 pending 说明内容已保存，**不要换新 request_id 重复提交**，等它补齐或调用 `index_reconcile`。
4. 用 `memory_inspect` 回读本次修订，按第 2 节逐条检查。

## 8. 可见范围（discovery）

- **一般不写**，由程序按记录类型给默认值：知识记录（L1–L4、关联、概念页）全库可见（workspace_summary）；目标、检查点、路线、问题等工作状态只在本对象可见（owner_only）。对象策略显式设置时以对象为准。
- 用户要求保密时显式写 `owner_only`。
- 不要把工作状态改成全库可见：它们由归属判定和续接按位置读取，不是知识；要跨对象复用就写成 L3 或结论。
- 修订记录时不写会沿用原值；要改变可见范围就显式写出，并在 `change_reason` 中说明。

## 9. 文稿

- 文稿根（document）按 `section_refs` 的顺序编排章节（document_section）。章节由作者写的衔接文字（prose，带依据）和整块收录的技术单元（unit）组成。
- research_process 是完整过程稿，research_report 是精简报告。按实际交付需要编写，可以只有一种；交付两种时依据必须一致。
- 文稿不会因为依据有新修订而自动改变。依据变化后用 `memory_document(view="impact")` 查看影响，再按 consolidate 流程处理。
